## 1. 整合前：两个插件是什么关系

一个**写入方 → 读取方**的闭环：

| | 写入方 | 读取方 |
|---|---|---|
| 产物 | `player-plugin/source-markers.lua`（mpv Lua，单文件、零外部依赖） | `extension/`（CEP 面板 + ExtendScript 引擎） |
| 宿主 | mpv 0.36 / 0.41（LuaJIT / Lua 5.1） | Premiere Pro 24.0.0 / Windows |
| 包体 | 22.4 MB（自带 mpv 本体） | 40 KB（两个变体共用扩展 ID） |
| 装法 | 绿色便携，解压即用，不写注册表 | 复制到 CEP 扩展目录 + 写 `PlayerDebugMode` |
| 耦合点 | `docs/marker-format.md`（格式 v1）——任何单边改动都会**静默**把标记放错位（无异常、无编译错） | 同左 |

两侧各自建过 release、各自做过真机验证，靠格式契约耦合。整合的价值在于：一次交付拿到完整闭环，
且两侧的实测结论能放在一起看。

## 2. 整合决策（含取舍理由）

| # | 决策 | 结果与理由 |
|---|---|---|
| 1 | **分发形态** | 一个包，但**两侧各自保留自己的安装方式**。没有合并成单一安装器：Pr 面板走 CEP 安装（写 `Program Files` + 注册表），播放器是绿色便携（解压即用、不写系统）。**安装方式本身就是两者各自的性质**，合并会破坏它 |
| 2 | **`release/` 写入权** | 本工作集只有解压后的目录，未涉及出包。后续出包建议保持「各自独立子目录」或单方统一出包，**不要两边都清 `release/`** |
| 3 | **格式契约** | **仍为 v1，未升版号**。只改了 `name` 列的**语义说明**；列数、列序、分隔符、CRLF、BOM、RFC4180 转义规则全部不动（见 §4.4） |
| 4 | **CEP 清单的版本写法** | **写数字 `1.0.1`，不写 `1.0.1-alpha`**。CEP 的版本由 Adobe 自己的 `Version` 类解析：`major.minor.micro` 为数字（上限 999999999），另有一个可选的 "special" 字符串位，且受 manifest schema 约束。带连字符的后缀是否被 schema 接受**无法在本机验证**（没有 Premiere），而失败的后果是**面板直接加载不出来**。所以 `alpha` 只出现在目录名与文档里 |
| 5 | **目录命名** | 跟随项目既有约定（`source-marker-1.0.0` 这种带版本的形式）→ `source-marker-united-1.0.1-alpha` |
| 6 | **两个原始发行目录** | **完全不动**，保留为逐字节可回滚的基线 |
| 7 | **整合记录的落点** | 就是本文（包内 `改动说明.md`）。工作区根的四份 md 保留为 v1.0.0 的**历史记录**，只在被推翻的地方加「已作废」标注，不改写历史 |
| 8 | **删除 `M01` 的语义选择** | 选「Pr 整列忽略 `name` + mpv 停止生成占位名」，而不是「Pr 删正则、mpv 继续写占位名」——后者会让**每条导入的标记注释里多出一个 `M01`**，比改前更糟。详见 §4 |

## 4. 行为改动：删除 `M01` 占位符机制

### 4.1 改了什么

- **写入方（mpv）**：不再生成占位名，标记的 `name` 一律为空串。
- **读取方（Pr）**：`smImportMarkers()` 里 `name`（payload 第 2 段）**整列忽略** —— 既不参与命名，
  也不进标记注释。标记名只取 `comment`（备注列）。

### 4.2 为什么

写入方生成 `M01`、读取方再按 `/^M[0-9]+$/i` 丢掉 —— **一来一回不携带任何信息**。
这是 Pr 面板当初参照 mpv 插件实现时带入的冗余。删除后 `name` 列的语义只剩「保留的列」。

### 4.3 兼容性

| 场景 | 结果 |
|---|---|
| **旧标记文件**（`name` 里带 `M01`）导入 Pr | ✅ 正常：`name` 被忽略，**不会**跑进标记注释 |
| 新导出的文件导入 Pr | ✅ `name` 为空，标记名 = `comment` |
| 用户手动在 `name` 列写内容 | ⚠️ **会被忽略**（`comment` 才是标记名） |
| 外部工具写的 `name` 经 mpv 转一手 | ⚠️ 会丢（因导出恒空）。这是选此方案的既定代价 |
| `mpv.conf` 残留 `source-markers-name_template` / `-fill_empty_name` | 无害：选项已不存在，mpv 会忽略 |
| 依赖 `name` 列的下游工具 | ⚠️ 需自行改为读 `comment` |

> **删除时唯一必须守住的点**：不能只删 Pr 那行正则。若 mpv 继续写占位名，
> Pr 会把它当「用户自填的名字」移进注释 → **每条标记的注释里多出一个 `M01`**。
> 两侧必须同时改，这正是本次的做法。

### 4.4 列与表头没变

CSV 仍是四列 `time,name,comment,color`；列序、分隔符、CRLF、UTF-8 BOM、RFC4180 转义规则全部不变；
JSON 仍带 `"name": ""` 字段。**没有任何列被删除或新增**，所以读取方的列别名映射不受影响
（格式文档特别警告过：新增命中别名正则的列会**静默覆盖**正列）。

## 6. 真机测试注意：**不要在工作集内运行 mpv**

实测（2026-10-06）：在工作集目录（`C:\Users\Frisk\Documents\Source_Marker_United`）内运行
`mpv.exe`，插件的写操作会被系统拒绝；把合并包整体移到工作集外（例如桌面）后导出恢复正常。

| 写入目标 | 工作集内运行 mpv | 备注 |
|---|---|---|
| 桌面 / 文档 | ❌ `Permission denied` | 两者 ACL 正常（`Frisk` = FullControl，无 Deny） |
| 工作集内、`%TEMP%` | ✅ | |

已排除的原因：ACL 损坏、「受控文件夹访问」（注册表键不存在 = 从未启用）、长路径（真实 Lua
`io.open` 实测 266/270/317/321 字符均成功）、插件自身（同一次测试里导出功能完全正常）。

**结论：真机测试请把合并包放在工作集外运行。** 若必须留在工作集内，就把视频与导出目标都放进
工作集内（或 `%TEMP%`）；此情形下视频旁的 `.marks.json` sidecar 同样写不进去，而它
**只记日志、不弹 OSD**，容易漏看。

## 7. 打包注意：运行会改写包内的界面状态文件

> **1.2.0「交织」更新**：该状态文件（`portable_config/source-markers-ui.json`）**已不再纳入版本库** ——
> 它是运行时状态（mpv 每次运行都会重写），不是源码。包内仍保留该文件；删掉它，首次运行会自动重建。

**`portable_config\source-markers-ui.json`**。只要从包目录里运行过一次 mpv，这个文件就会被改写
（记住 `panel` / `hint_shown` 状态）。

- 它**不在** `SHA256SUMS.txt` 的 16 项覆盖范围内，`校验.ps1` 仍会全绿；
- 但「解压后直接用」会改动包内文件。若要做**逐字节可复现的发行包**，请在打包脚本里把这一项
  重置为模板原值（本包为 `{"hint_shown":true,"panel":false}`）。

一次只动一处。

## 11. r3 / r4：一键互跳

对应 §9 第③项。**目的**：在 Pr 里点一下，用 mpv 打开同一素材并停在同一时间点。

### 11.1 先解决了一个前置问题：两边的时间戳对不上

用户实测发现 Pr 的时间码与播放器（MPC-HC / mpv）在同一帧上会随片长线性发散，量级约 3 s/小时。
用生成的参考视频（`参考视频/`，CFR + VFR 各一份、60 分钟、6 个彩色单帧检查点）测完，结论是：

**这不是 Pr 的 bug，是 24fps 非丢帧时间码对 23.976 素材的标准行业惯例。** 精确关系：

```
Pr 时间码秒 = 帧号 ÷ round(容器帧率)        真实秒 = 帧号 ÷ 容器帧率
→ 真实秒 = Pr时间码秒 × round(fps) / fps      （23.976 时 = 1001/1000，精确）
```

60 分钟处偏差 −3.596 s，与「3 s/h」吻合；6 个检查点拟合残差为 0。

**关键的反直觉结论：这个偏差只活在「人眼看的时间码字符串」里。** 底层数据两边是一致的 ——
`app.sourceMonitor.getPosition().seconds`（与 `getInPoint().seconds` 同源，面板实测确认是
**真实秒**）与 mpv 的 `time-pos` **同一量纲**。

> 完整推导、VFR 的 conform 结论、以及「`.seconds` 是真实秒」的判别过程，见
> `参考视频/README.md` 第六、七节。

### 11.2 所以互跳不需要任何换算

| 侧 | 拿到的量 | 量纲 |
|---|---|---|
| Pr | `smGetPlayerPosition()` → `app.sourceMonitor.getPosition().seconds` | **真实秒** |
| mpv | `--start=<同一批真实秒>` | **真实秒** |

**零换算、零校准、零"记住偏移量"。** 唯一要守的纪律：**不走时间码字符串**。

### 12.7 r6：修掉一个「活儿干成了却报失败」的 bug（用户真机发现）

**现象**（装/卸其实都成功了，但结论栏报「有步骤失败」）：

```
 有步骤失败：
   - Pr 面板（退出码 安装 Source Marker  源目录 : … 安装完成。 0）
```

**根因：PowerShell 的函数返回值污染。**

```powershell
& powershell @a           # ← 子进程 stdout 混进了本函数的返回值
return $LASTEXITCODE      # ← 于是"退出码"变成数组，末尾才是 0
```

于是 `$code -ne 0` 成了「数组 ≠ 0」——**恒为真**，连 `exit 0` 的成功也会被判成失败。

**复现证据**（本机 5 行内可重现）：

```
旧写法：返回类型 = Object[]  元素数 = 2
$o -ne 0 的结果 = [hello-from-child | 3]  → 判为【失败】
```

**修法**（本机可验证，不依赖 `Start-Process`）：

```powershell
& powershell @a 2>&1 | Out-Host      # 输出送进主机，不进管道
return [int]$LASTEXITCODE            # 保证是 Int32
```

`2>&1` 是先把 stderr 并进来 —— 否则 PS 5.1 会把原生命令的 stderr 包成
`NativeCommandError`，在 `$ErrorActionPreference='Stop'` 下可能中断父进程。
验证：子进程 `exit 3` → 返回 `Int32 3`（正确判失败）；`exit 0` → 返回 `Int32 0`（正确判成功）。

**同轮顺手修的两处**：

1. 卸载时第 3 步不再打印「没找到已安装的 Pr 面板」—— 第 1 步刚把扩展目录删掉，"找不到"是正常的。
2. 提权提示改成诚实的：原来无条件说「已在新窗口继续」，但 `Start-Process -Verb RunAs`
   在 UAC 没放行时**也可能不抛异常**（本机沙箱里就复现了这个情况：什么都没装，却打印了"已在新窗口继续"）。
   现在改成「已请求提权 + 没出现新窗口就右键以管理员身份运行」。
   **顺带证实那次冒烟没有改动系统**：已装的 `main.js` 是完整版 r5（`D9929E1A`），
   而冒烟目标是新手版 r6（`B238C5EE`）—— 完全不同的文件。

**教训（值得进项目方法论）**：PowerShell 里「函数返回值」与「子进程输出」共用同一条管道 ——
**凡是在函数里调外部程序并想拿退出码，必须先把输出引开**。这和交接文档那条
「ExtendScript 返回值一律不可信」是同一类毛病：**别把"调用了"当成"拿到结果了"**。

### 12.8 我自己踩的坑：**不要拿安装器当冒烟测试**

验证 r6 时我想"跑一下看它会不会报错"，以为请求提权就会被拦下
（`Start-Process -Verb RunAs` 在无界面环境下应当失败）。**结果 UAC 确认框弹了出来，用户顺手点了「是」，
脚本真的执行完了**：

- 用户已装的**完整版 r5 被覆盖成新手版 r6**
- 因为 `install.ps1` 会先清空目标目录，**`player-path.txt` 一并被删掉**

影响面：面板被换成了新手版；「用播放器打开」第一次会要求手选播放器（保险绳照旧生效，不是坏掉）；
「打开方式」注册未被触碰（那次用的是 `-PrOnly`）。
恢复：同步 r6 到桌面后重跑一次 `安装.cmd`（选你想要的变体）—— 面板与 `player-path.txt` 都会写回。

**教训：安装器的"冒烟测试"就等于真的安装。** 安全做法只有两种：
① 用 `-DryRun`（子脚本 `install.ps1` 有，本脚本**待补**）；
② 或者根本不跑，只做静态检查（PS 解析 + 文本核对），把"真的跑一遍"留给用户。

**订正**：我最初写的是「本机 UAC 会静默放行」—— **不对**。事实是 UAC 确认框弹出来了，
用户顺手点了「是」（本人确认）。这也解释了为什么第一次冒烟"看起来什么都没做"（没点确认）、
第二次却真的装了。

**由此定下一条工作规矩**：**凡是要改动系统 / 有风险的操作（安装器、注册表、写 Program Files、
提权），必须先提醒用户并等确认，不能自己"试一下"。**

**已补上安全出口**：`install-united.ps1 -DryRun` —— 只打印将要做什么，
**不改文件、不改注册表、也不提权**（提权分支是 `-and -not $DryRun`）。
子脚本 `install.ps1` 本来就有 `-DryRun`，这里把它一路透传下去。

**DryRun 的预测也要准**：第一版里第 3 步打印「现在没找到已安装的 Pr 面板 —— 实际执行时这一步会被跳过」，
但真实安装时第 1 步会先把面板装好，所以这一步**不会**被跳过。现已按方向分开预测：
安装方向报「[将写入] …\player-path.txt（第 1 步刚装好面板，所以这一步会真的写入）」，
卸载方向报「第 1 步会删掉扩展目录，这一步实际无事可做」。**DryRun 的价值全在预测准。**

**验证方式本身也有坑（本轮第二次踩）**：用 `… 2>&1 | Select-Object -First N` 截断
**原生命令**的输出时，`-First` 会提前终止上游管道 → **子进程被杀** → `$LASTEXITCODE` 变成 `-1`。
本轮卸载方向的 DryRun 就这样被误报成 `exit = -1`，去掉 `-First` 后是 `exit = 0`。
**教训：拿原生进程的退出码时不要截断它的输出流** —— 要留就重定向到文件再挑。

DryRun 的只读性用**前后状态快照对比**证明：连跑三次（安装方向 ×2、卸载方向 ×1），
扩展目录与注册表 `RegisteredApplications` 逐字节一致，零改动。

## 13. r7 – r11：Pr 面板这一轮（自动刷新 / 导入对照 / 导出）

对应需求原文三条：

1. 源监视器「刷新手动」问题 → 自动化（**稳定性与资源消耗要一并考虑**）
2. 导入窗口做左右对照 + 用颜色表现标记色
3. 新增「导出当前源的标记」，保持互通格式（Pr 侧此前**只能导入**）

### 13.1 自动刷新（r7）

**为什么只能轮询**：Pr 的 ExtendScript 侧**没有**"源监视器变了"的回调，也没有事件通道。

**做法**：轮询 `smGetState` —— 它本来就返回刷新界面所需的全部字段，**一次调用即一次刷新**。

**四条纪律**（都是为稳定性与开销）：

| # | 纪律 | 原因 |
|---|---|---|
| 1 | 上一次没回来就不发下一次 | 请求不叠加，不拖慢 Pr |
| 2 | 只在状态真变了才动界面 | 避免无谓重排 / 抢焦点 |
| 3 | **正在输入的时间码框不覆盖** | 否则轮询会把用户打的字擦掉 |
| 4 | 某次调用卡住超 10 秒 → 警告一次并放行 | 避免轮询**永久停摆**（静默失效最难查）|

间隔 2 秒；勾选框「自动刷新」可关，**选择会被记住**（写进现有 `SET`）。

### 13.2 标记颜色：不是猜的，是探出来的

导出与对照都要"读标记颜色"，但 ExtendScript 的 `Marker` 只有写用的 `setColorByIndex()`，
**读的 API 查不到**（Adobe 论坛有人专门发帖问 *Getting Marker Color via Script*，这本身就是信号）。

按本项目的老办法**压成一次点击**：在完整版「自检」里加一条**受控回读**探针 ——
自建一个标记、写死颜色 3、再试 5 个候选读法、枚举方法名兜底、最后自删。

**真机回报（Pr 24.0.0）**：

```
标记颜色读取（自建自删） :: 已写 setColorByIndex(3) → getColorByIndex:function=3
    getColorIndex:undefined=-  getColor:undefined=-  colorIndex:undefined=-  color:undefined=-
    ／ 可枚举方法=[宿主对象不可枚举] ／ 清理后标记数=1
```

**结论：`marker.getColorByIndex()` 可用**（写 3 读回 3）。探针自建自删，不留痕迹。

### 13.3 导入对照两栏 + 颜色（r8）

- 左栏「源里现有的标记」：复用已有的 `loadMarkers()` 渲染
- 右栏「文件里的标记」：**选完文件立刻**用面板自己的 `parseMarkerFile()` 解析并渲染，
  **点「导入」之前就能对照**（全程不需要引擎参与）
- 两栏都按标记自己的颜色着色（文字色 + 左侧色条），色值取契约 §4 的参考色值
  ——**只用于界面展示，不参与交换**（文件里只有索引）

#### ⚠️ 协议变更：标记列表回传从 3 字段变 4 字段

`smListMarkers` 原为 `秒|名|注释`，现为 **`秒|名|注释|颜色`**（颜色读不到时给 `-1`）。
面板与引擎是一起发的，所以自洽。但：

> **下游若有用例/工具断言"标记列表字段数 = 3"，必须同步更新。**

面板侧对 `f[3] === undefined` 是容错的（当作 `-1`、不着色），所以**老引擎配新面板仍可用**。

### 13.4 导出到源目录（r9 → r11）

Pr 侧从此也是**写入方**，必须满足契约 §6 的写入方保证。逐条对照：

| 契约要求 | 实现 |
|---|---|
| CSV 带 UTF-8 BOM | `'\uFEFF' + buildMarkerCsv(...)` |
| 行尾 CRLF、末尾也给一个 | `lines.join('\r\n') + '\r\n'`（与 Lua 逐字节对齐）|
| 只写四列 `time,name,comment,color` | 表头字面量 |
| `name` 列一律写空 | `csvField('')` |
| `time` 默认毫秒 | 先整毫秒取整再拆位（零误差）|
| RFC4180 转义 | 含 `"` `,` CR LF 才加引号，内部 `"` → `""` |
| 升序 | `sortedMarkers()` |
| JSON **不带** BOM | 直接 `JSON.stringify` |
| JSON 的 `tc` | **整秒 + 真实帧率帧号 + `⌈fps⌉` 进位**（禁用"总帧数取模"）|
| 空列表不产出文件 | 提前返回并提示 |
| 同时产出同名 `.csv` 与 `.json` | 与 Lua 的 `export_to` 一致 |

**落盘约定**（这条决定能否被「自动找标记」认出来）：`<素材名>_markers_<YYYYMMDD-HHMMSS>.csv`
放**素材同目录** —— 正是 `findMarkerCandidates()` 找的规则，也正是 mpv 侧的写法。
素材目录**写不进去**时（只读共享 / 权限）才退回面板的「输出目录」，
并**在日志里说明用的哪个**，绝不静默换地方。

**写入方对齐的两个细节**（都是重读 Lua 源码才发现的，靠记忆会写错）：

- `created` 是 **UTC 带 `Z`**（`os.date('!%Y-%m-%dT%H:%M:%SZ')`），不是本地时区偏移
- 文件名里带**时间戳**（`%Y%m%d-%H%M%S`），不是 `<stem>.csv`

### 13.5 ⚠️ 最重要的教训：`name` 与 `comment` 是两个不同的东西

**这里已经骗过我们一次，务必记住。**

| | 是什么 |
|---|---|
| 文件的 `comment` **列** | ↔ Pr 标记对象的 **`name` 属性**（Pr 界面显示的就是它）|
| 文件的 `name` **列** | 另一个东西 —— 契约 §1.2 里那个被读取方整列忽略的遗留占位列 |

引擎的 `smImportMarkers()` 就是这么写的（**第 563-564 行**）：

```js
m.name = rawNote;      // 文件的 comment 列 → 写进 Pr 的 name 属性
m.comments = '';       // comments 恒空
```

而 r9 的导出只读了 `m.comments` → **恒空** → 真机表现为
「导出丢掉 Comment，只剩 time 和 color」。

**修法**：抽一个 `markerBody()`，**显示与导出共用同一条规则**：

```js
function markerBody(m) { return (m.text != null) ? m.text : (m.name || m.desc || ''); }
```

- 源标记：`loadMarkers` 显式算 `text = name || comments`（name 优先）
- 文件侧标记：显式算 `text = comment 列`（契约 §1.2：name 列整列忽略）
  —— **两者语义不同，所以分开算，不能用一个规则糊过去**
- 导出与显示都走 `markerBody` → **不可能再各说各话**

> 附带教训：这条规则最初在 `markerRowText` 与 `toExportRow` 里**各写了一遍**，兜底顺序还相反
> （`desc||name` vs `name||desc`）。是离线测试把它们对拍出来的。
> **规则写两遍，就迟早会分叉。**

回归测试已钉死，含一条**反向断言**：证明"只读 `desc` 的老写法"确实会丢正文 ——
谁改回去，测试立刻炸。

## 14. r12 – r16：面板交互这一轮（刷新间隔 / 日志分级 / 标记增删改 / 两个 CEP 边界）

### 14.1 布局：要能塞进 400 宽 × 350 高

**拦路石（先发现的）**：清单里的 `MinSize` 原来是 **420 高 × 320 宽** —— 也就是说
Pr **根本不允许把面板拖到 350 高**，光改样式没用。已下调为 **340 高 × 300 宽**（默认 Size 仍 400×640）。

**三条原则**：

1. **行必须能换行**：`.row { flex-wrap:wrap }` —— 原来没有，400 宽时那一行
   （间隔框 + `ms` + 列出标记 + 导出到源目录 + 导入）必然横向溢出；
2. 内外边距全线收紧（body 10→6、section 8/9→6/7、按钮内边距下调）；
3. 列表与日志高度收敛（日志 110/96→88/80；标记列表 132→104/96）。

**两处细节**：`#tcLine { flex:1 1 100% }`（时间码那行文字长，独占一行最稳）；
`input.ms { flex:0 0 58px }`（否则继承 `input { flex:1 }` 会被拉得老长）。

**一句实话**：内容约 750px 高，在 350 高里**必然纵向滚动** —— 这是功能量的结果。
保证的是：不横向溢出、不裁切、不重叠、每个区完整可用。想完全免滚动只能把不常用的区做成可折叠。

### 14.2 自动刷新分两路（r12）

| 路径 | 调用 | 默认间隔 | 覆盖 |
|---|---|---|---|
| 源状态 | `smGetState`（轻）| 2000 ms | 素材名/路径、入出点、时间码 |
| 标记列表 | `smListMarkers` | 5000 ms | 标记内容 |

- 两个间隔都能在面板上填，**自动夹到 300–60000**（填 0 不会把 Pr 轮询死），选择会记住；
- 标记列表按**内容签名**（`时间|正文|颜色`）判断 —— 覆盖「改颜色 / 改注释 / 在时间轴上拖动标记」
  这些**不改变条数**的编辑（r7 只按条数判断，所以那些情况一直刷不出来）；
- **内容没变就不重绘**：否则每 5 秒重绘会冲掉滚动位置与选中项（14.4 的选中就靠它）。

### 14.3 日志分级与清空（r12）

INFO / OK / WARN / ERR 四级，各自颜色 + 左侧色条。老调用
`log(x)` / `log(x,'ok')` / `log(x,'err')` **全部照旧可用**（向后兼容）。另加「清空」按钮。

### 14.4 标记的选中 / 编辑 / 删除（r14）

- 单击：选中（蓝底）+ 跳到该标记
- 双击：改正文
- 选中后 Delete：**两段式** —— 第一次该行变红 + 黄色警告，**3 秒内再按一次**才真删
- **不用 `window.confirm` / `window.prompt`** —— CEP（CEF）里常被禁用，属于不可验证的坑

**核心：绝不盲操作。** 引擎 `_markerAt()` 用「**下标 + 期望时间**」双重定位：

```
① col[下标] 的时间对得上（容差 0.08s ≈ 2 帧）→ 用它
② 对不上 → 整列里找时间最接近的
③ 最近的也差 > 2 秒 → 返回 null，两个调用方一律报错退出，什么都不做
```

面板拿到列表到用户点击之间，Pr 里的标记可能已经变了（自动刷新刚更新过列表），
**光凭下标可能删错人**。下标只是提示，时间才是凭证。

另外：**选中按时间记，不按下标** —— 自动刷新重绘后不会错位。
写入位置是 **`m.name`**（理由见 §13.5）。

### 14.5 ⚠️ CEP 面板的中文输入法：候选窗位置不可靠（**面板全境**）

**现象**：候选浮窗出现在窗口左上角，不跟随光标。

**关键定性（用户实测）**：**面板里所有文本输入框都一样** —— 不是某个输入框的问题，
是 **CEP/CEF 层的通病**。

**试过但无效的做法**（假设被实测否掉，记下来免得再走一遍）：
把输入框移出 `overflow:auto` 的 `.mklist` 与 `overflow:hidden` 的 `.mk`，
原以为 CEF 上报的"光标矩形"会被这类可滚动/裁剪祖先影响 —— **移出后现象依旧**。

**有效解法：走原生对话框。** ExtendScript 的 `prompt()` 是**原生模态对话框**，
输入法由系统摆位，跟随正常。引擎封装为 `smPromptText(title, default)`，
面板双击标记时优先用它；引擎若回"没有 prompt"，才退回面板内编辑条。

**踩到的坑**：`prompt()` 取消时返回 `null`，但**常常变成字符串 `"null"`** ——
判空必须两种都拦，否则点 Cancel 会把标记正文写成**字面量 `null`**（真机已踩，已进回归测试）。

**协议安全**：用户输入里的 `US(0x1f)` / `GS(0x1d)` / `RS(0x1e)` 与换行一律折叠成空格，
否则会把面板↔宿主的回传协议撑破。

### 14.6 ⚠️ Pr 的活动监视器：面板改不了（能力边界）

**现象**：点面板里的标记跳转后，Pr 的活动监视器仍留在「节目」→
按空格播的是**序列**而不是源。

**真机自检实测（Pr 24.0.0）**：

```
app.sourceMonitor.play = function      ← 唯一存在的入口
activate / setActive / open / openInSourceMonitor / bringToFront 全部 undefined
```

**两次尝试都无效，机制已被用户观察查清**：

| 做法 | 现象（真机）|
|---|---|
| r16：跳转后调 `play(0)` | 源监视器的传送按钮**变成「暂停」方块**，但画面不动 |
| r17：脉冲 `play(1)` → `play(0)` | 按钮**瞬间来回切一次**，随后同上 |

**结论**：`app.sourceMonitor.play(speed)` 只控制**源监视器自己的传送状态**，
**完全不碰"哪个监视器是活动监视器"**；而且 `play(0)` 会把传送按钮留在"暂停"外观上
（"以 0 速播放"的 UI 表现）—— 一个**平白留下的副作用**。

**已定案，不再硬凑**：这是 CEP 的能力边界。Pr 的活动监视器只能由用户在 Pr 里
**点一下目标监视器面板**来切换（Pr 会记住），之后按空格才会播源。
面板里**移除**了那次偷偷调用（副作用大于收益）。

**但 `play(1)` 确实能播源** —— 于是把它做成面板上的「**播放源 / 暂停源**」按钮
（引擎 `smPlaySource(speed)`）：它控制的是源监视器本身，所以
**即使活动监视器是节目，也能从面板直接播源**，不必再去点 Pr 的监视器。
已知小瑕疵：在 Pr 里自己按空格/停之后，按钮文案可能暂时滞后 —— 再按一次即可对齐。

### 14.7 验证手段的增量

## 15. r19 / r20：入出点栏的清理与微调跟随

### 15.1 删掉「源入出点 ⇄ 序列入出点」（r20，用户决定）

两个按钮 + 面板处理器 + 引擎函数（`smPushInOutToSequence` / `smPullInOutFromSequence`）
**三处一并删除**。

**原因是坐标系不同**：

| 概念 | 是什么 |
|---|---|
| 序列入出点 | **时间线上的位置**（`seq.getInPointAsTime()`）|
| 片段入出点 | **素材内部的位置**（`item.setInPoint`，`MEDIA_ALL`）|

把数值从一个直接搬进另一个，一般**没有意义** —— 只有"序列从 0 开始且片段也从 0 开始"
时才碰巧相等。原来完整版上的标签（`← 序列入出点` / `源入出点 →`）又过于简略，
新手版那套（`读取时间线的入出点` / `写到时间线`）也只是把意图说明白，坐标系问题依旧。

**原引擎位置留了一条墓碑注释**，写明原因与「要恢复请先定清语义（例如换算成片段内的相对位置），
不要照搬旧实现」—— 免得后人把错的东西再捡回来。

顺带把「清除」明确为「**清除源入点和出点**」（原来只说"清除"，不知道清的是谁）。

### 15.2 微调时播放头跟随（r20）

原来微调只改数值、播放头留在原地，改完还得自己再按一次「跳到 In/Out」。

现在：`smNudge` 成功后，把它**已经回传的**新位置交给现成的 `seekTo()`（走 QE），
**播放头跟着走到新的入/出点**。

> 没有新增任何引擎能力 —— 复用了已存在的回传字段（`fields[0]` = 新秒数）与已有的跳转函数。

### 15.3 开发按钮搬家（r19）

「自检」「探测 QE」从入出点栏搬到**日志栏右侧**（并加了悬浮说明）。
纯标记移动：按钮 id 没变、绑定按 id，**JS 一行未改**。新手版本来就没有这两个按钮。

### 18.6 r25：我的校验容差在骗人（本轮最重要的教训）

真机日志：

```
OK 微调 In +1 帧 → 2.000 | VERIFIED    ×3      ← 值根本没动，却报 VERIFIED
```

根因：读回校验的容差写死 **0.05 秒**，而这个素材是 **30 fps —— 1 帧只有 0.033 秒** ✓
→ **整整差一帧反而落在容差之内** ✓ → 被判成功 ✓

> **教训：校验的阈值必须与被测量的最小单位挂钩。**
> 一道阈值太松的校验**比没有校验更糟** —— 它会制造虚假的把握。
> 现在改成 `0.5 / fps`（**半帧**），1 帧的偏差必须被认出来。

同时加了一条重试路径：seconds 写不进去时改用 **ticks**（Pr 的原生时间单位；
ticks/秒从对象自身推算，实测 34.72s ↔ 8819435520000 ticks）。

### 18.8 待解：`＋` 微调无效

真机 `r25` 日志（30fps 素材，`＋` 共 11 次全失败、`−` 有时成功）：

```
微调 In  +1 帧 → 2.000  | MISMATCH-CHECK 请求=2.033  现=2.000   ×4
微调 Out +1 帧 → 16.033 | MISMATCH-CHECK 请求=16.066 现=16.033  ×7
```

- **两种构造都失败**（`r=null/null` = seconds 与 ticks 两条路都没生效）→ 所以**不是构造方式的问题**
- 失败时的读回值都**落在帧格上**，且**总是小于等于请求值**
- **r26 试了"先清空再设"**：真机证明**无益**，而且会让源监视器的入出点**可见地闪一下**
  （用户观察："入出点会瞬间漂移到源的最初/最末点然后再瞬移回来"）—— 已移除；
  `clearInPoint/clearOutPoint` 只保留在「清除源入点和出点」按钮里。

### 18.9 r27：根因锁定 —— `frameRate` 报的不是帧格

**决定性证据是 r26 日志里的这一行**（我为了让算术可核对才加的那个字段）：

```
fps=30.0010200353898
```

而同一份日志的读回值 —— `2.000 / 2.067 / 2.133 / 2.200 / 2.267 / 2.333 / 2.367 / 2.400` ——
**全是 1/30 的整数倍** ✓

→ **`footageInterpretation.frameRate` 报 30.00102…，而 Pr 把媒体时间存在「整数帧率」的格上** ✓
→ 用 `1/30.00102` 去加，目标落在帧边界**下面一丁点**（约 1e-6 秒）→ **Pr 把它对齐回原帧** →
表现就是"请求 2.033、读回 2.000，完全没动" ✓

**这一个根因解释了用户观察到的三件事**：
1. `＋` 从不生效、`−` 时好时坏（累积误差相对边界的方向随起始值而变）
2. **改成跳 2 帧就"好像好了"** —— 0.0666 远大于 1e-6，能跨过边界
3. **在源监视器里手动设一次入出点就能好一阵** —— 手动落点正好在格上，之后几次还没跨过边界

**修法**：先换算成**帧号**、加减、再按 `round(fps)` 换回秒 —— 目标必然落在帧上 ✓
（与项目既有的"时间码真值"结论一致：**Pr 的帧号基准就是 `round(fps)`** ✓）
半帧容差也顺势改成以 `round(fps)` 为准 ✓

> **方法论收获**：真正破案的不是我猜的任何一个机制，而是**我为了让算术可核对而多打的那个 `fps=` 字段**。
> 教训：**把中间量打进日志，比多想三个假设更有效。**

### 18.10 r28：`round(fps)` 也是错的 —— 帧率要**判别**，不能写死

r27 的真机反馈：**两个较短的测试源通过**，但换成**时间码素材（23.976、1 小时长）**又失败：

```
微调 Out -1 帧 → 3599.805 | MISMATCH-CHECK 请求=3599.833 现=3599.805 起始=3599.888 帧率=24
```

**判别式**：Pr 的入出点**必定落在它自己的帧格上** —— 也就是「起始值 × 真帧率 ≈ 整数」：

| 素材 | `frameRate` | 起始值 | × `frameRate` | × `round(frameRate)` |
|---|---|---|---|---|
| 23.976 | 23.976023976 | 3599.888 | **86311.0 ✓ 整数** | 86397.31 ✗ |
| 30 | 30.00102 | 2.000 | 60.002 ✗ | **60.0 ✓ 整数** |

**两种素材的"真帧率"正好相反** ✓ 所以 r27 写死 `round(fps)` 必然错一半 ✓

读回值本身也自证了这一点：`3599.805 = 86309 × 1001/24000 = 3599.8045` ✓
—— 它落在 **1001/24000** 的格上（真 23.976 时间戳），**不是** `n/24` ✓

**修法**：用「哪个率能让起始值落在整数帧上」来**判别**（门槛 0.001 帧）；
容差收紧到 **0.1 帧**；失败时把**实际移动了几帧**一并报出 ✓

**用户补充的关键观察**（对今后排查极有价值）：

> 问题具有连续性 —— 如果手动设置出入点后第一次 ± 偏移没问题，那么接下来无论点多少次都不会报错。

即**成败取决于起始值落在哪个格上**，不是随机 ✓ 与上面的判别式完全吻合 ✓

**VFR 素材**（`frameRate=17.9659`）：没有均匀帧格，"移动 1 帧"本身就不是精确概念 →
日志改为报「实际移动=N 帧」让人判读；同时**面板日志改为按判定上色** ——
引擎的 `ok=true` 只代表"调用没报错"，MISMATCH 不能再被刷成绿色的 OK（同一类"制造虚假把握"的错误）✓

### 18.11 r29：真相 —— 落点正好压在帧边界上，而 Pr 的 ticks 转换是**截断**

r28 真机日志（23.976 素材）：

```
起始=1853.310 请求=1853.351（正是 +1 帧）→ 现=1853.310   实际移动 0.00 帧
起始=1853.643 请求=1853.602（正是 −1 帧）→ 现=1853.560   实际移动 −2.00 帧
```

**请求值本身完全正确**（恰好差 1 帧，率也选对了）—— 是 **Pr 把落点退到了前一帧** ✓

**根因**：目标值**正好落在帧格边界上**；Pr 把 Time 转成 ticks 是**截断**的，
浮点噪声只要让落点掉到边界**下面一丁点**（1 ULP 量级），Pr 就退一帧 ✓

**这一条把整段历史全部串起来了**：

| 现象 | 解释 |
|---|---|
| 时好时坏 | 噪声落在边界哪一侧是随机的 |
| 失败有连续性（第一次好就一路好）| 噪声方向一旦固定就一路对 / 一路错 |
| 改成跳 2 帧"好像好了" | 2 帧的余量盖过 1 ULP |
| `+2` 能过、`+1` 不动 | 同一机制 |

**修法**：落点往目标帧**内部**推帧长的 **1%**（≈0.4 ms）✓
尺度：ticks 分辨率 ≈ 4e-12 秒、浮点噪声 ≈ 1e-13 秒 —— 1% 帧比它们大好几个数量级，又比一帧小 100 倍 ✓

**校验比的是「理想落点」（不含 eps）**，所以 `VERIFIED` 的语义没有变松 ✓

> **方法论（三轮的共同教训）**：真正推进的从来不是我猜的机制，而是**新打进日志的中间量** ——
> `fps=`（r26）→ `率=` + `实际移动=`（r28）→ 每一步都比"再多想三个假设"有效。
> 而"阈值太松的校验"和"失败也刷成绿色 OK"是同一类错误：**制造虚假的把握**。

### 18.12 结案：8 轮 + 一个可复跑的证明

**最终结论（用户真机复测，逐字）**：

> 无论是前后跳、跳多少帧，无论是 30fps 短、59.97fps 长、23.976 CFR 1h、甚至是 VFR 上测试，都是 VERIFIED！

**可复跑的证明（离线，不依赖 Pr）**：按 Pr 的**截断**语义模拟 29.9 万帧 ——

| 写法 | 会退到前一帧的比例 |
|---|---|
| 落点正好压在帧边界（r28 及之前）| **44.2%**（132124 / 299000）|
| r29（推入目标帧内部 1%）| **0.0%** |

> 例：第 1000 帧应有 `10594584000000` ticks，浮点算出 `10594583999999`（**差 1 tick**）
> → 截断后落到第 999 帧；加 eps 后正确落在第 1000 帧 ✓

**44.2% 正好解释了用户观察到的"时好时坏"**；而"失败具有连续性"同样吻合 ——
某个起始值要么中招、要么不中招，之后一路固定 ✓

**八轮时间线（每一轮都缩小了一次包围圈）**：

| 轮次 | 假设 / 动作 | 结局 |
|---|---|---|
| r22 | 跟随跳转打爆 QE | ✗ 被实测证伪（关掉跟随仍卡）|
| r23 | 请求叠加（异步队列堆积）+ 引擎边界保护 | ✅ **卡死真正解决** |
| r24 | "沉默"本身就是问题 | ✅ 看门狗 + 成功也记日志 |
| r25 | 校验容差太松（0.05 秒 > 1 帧）| ✅ 纠正"制造虚假把握" |
| r26 | Time 带着旧范围上下文 | ✗ 无效且引入闪烁；**但 `fps=` 字段成为破案关键** |
| r27 | 帧格就是整数帧率 | ✗ 只对一半素材 |
| r28 | 帧格要**判别**不能写死 | ✅ 率选对了 |
| r29 | **落点压在边界 + ticks 截断** | ✅ **全部通过** |

**留下来的三条方法论（比修好的 bug 更值钱）**：

1. **把中间量打进日志** —— 破案靠的是 `fps=`（r26）、`率=`/`实际移动=`（r28），
   而不是任何一次"再多想几个假设"。
2. **阈值太松的校验比没有校验更糟** —— 写死 0.05 秒的容差在 30fps 下比 1 帧还大（r25）。
3. **失败不能刷成绿色 OK** —— 引擎的 `ok=true` 只代表"调用没报错"，
   判定（VERIFIED / MISMATCH）要单独上色（r28）。

**用户侧的观察是解题的一部分**：三次关键校正都来自用户 ——
「跟随关掉仍卡」（否掉 r22 的假设）、「失败具有连续性」（指向"状态相关"而非"随机"）、
「改成跳 2 帧就没事」（指向 ULP 量级的余量）✓

2. **PowerShell 引号**：双引号字符串里再写双引号会直接解析失败（我在本项目里犯了两次）；
   中文内容一律走**单引号 here-string**。
3. **`(if(...){...})` 不能当表达式**（本环境不支持）—— 拆成独立 `if` 语句。
4. **`Select-Object -First N` 接在原生命令之后会截断输出流并毁掉退出码**（犯过两次）—— 读退出码时不要截断。
6. **验证脚本别依赖"顺手的通道"**：我曾用命名管道给 mpv 发 IPC 指令做功能测试，在 `danger-full-access`

   于是把"文件根本没被改写"误读成"修好了"**假阳性**。→ 规矩：**测试必须断言"动作真的发生了"**
   （这里改成用 `--frames=1` 让 mpv 自然退出、走 `shutdown` 处理器，再读文件内容对比）。
7. **mpv 命令行上的 `--script-opts=` 会替换掉 `mpv.conf` 里的同名选项**（它是列表型选项）——
   我在复现 bug 时顺手加了一句 `--script-opts=source-markers-sidecar=no`，结果把真正要验的
   `panel=yes` 一起顶掉了，A 步因此"没复现"。→ 复现类测试要**完全按真实使用方式**跑，别加无关参数。
9. **替换脚本里绝不能留"试验行"**：我在同一个脚本里留过 `P '…' '…'`（函数名写错）、
   `Patch $h.F $h.F2 …`（参数写错 → 退化成"空字符串搜索"，903 次命中）、
   `Patch $J2 "…" "…" 0`（把它当"探测"用，而真实计数是 1）—— 四次都被"命中数不符即抛错"拦下，
   **零损坏**，但每次都白跑一轮。
   → **规矩**：每一条替换都必须带**来自刚读出的真实计数**；**不要写"探一下"的调用**；
   脚本发出去前自己扫一遍有没有多余行。8. **`robocopy` 的 `/XD` 只排除目录、`/XF` 才排除文件**：我把 `ffmpeg.exe` 误写成 `/XD`，
   分支工作副本里多进了 208 MB（所幸 `.gitignore` 拦住了它，从未入库）→ 排除文件一律用 `/XF`。5. **mpv 运行时锁住整个包**：面板「用播放器打开」是从包内启动 mpv 的 → 此时**包不能被改名 / 移动 / 删除**。
   诊断实录：包内 64 个文件**全部可独占打开**（说明**不是文件锁**），而是**目录级句柄**；
   关掉在包内打开的资源管理器窗口 / 终端后即恢复正常。

## 23. 1.2.0「交织」③：标记模式（F10）

**目标**：把十几个 Ctrl/Alt 组合换成"Pr 源监视器"那套裸键。因为 mpv 里裸字母全被它自己占了
（`m` = 静音 等），所以做成**模式**：`F10` 开关，开启后接管 4 个键，**右下角常驻小标**。

| 键 | 动作 | 出处 |
|---|---|---|
| `M` | 在当前播放头打标记 | Pr 键位表（M 添加标记）|
| `Shift+M` / `Ctrl+Shift+M` | 下一个 / 上一个标记 | 同上 |
| `Del` | 删除播放头处的标记 | 你的意见：不加 Ctrl+Shift+Alt+M 清除全部 |

**先实测再动手**（这一步很值）：用 `keypress` 真喂键做三方对照 ——
脚本绑定 vs mpv **内置**绑定 → **脚本赢**；脚本绑定 vs 用户 **input.conf** → **input.conf 赢**。
结论：包内只发 `input.conf.example`（不发 `input.conf`），**默认情况下模式键能可靠接管**；
但用户一旦自定义同名键就会盖掉模式 → 所以既有 `Ctrl+m` 等快捷键与 F2 面板**全部保留**作保底，
启动日志、帮助浮窗、input.conf 示例、快速上手里都写明这条规则。

**真机 A/B/C/D**（每例先重置界面状态，`keypress` 喂键）
- A 模式关按 `m` → 加标记 0 次 ✅（`m` 仍归 mpv）
- B `F10` 后按 `m` → 加标记 1 次 ✅（证据链：绑定已启用 4 键 → 按键→add → 已加标记）
- C `F10` 开→关后按 `m` → 加标记 0 次 ✅（关得掉）
- D 模式内 `Shift+M` / `Ctrl+Shift+M` / `Del` → 三个键都到达脚本 ✅

**过程中查清并写进代码注释的 API 事实**
- `mp.add_key_binding` 的**返回值在本机 mpv v0.41.0-dev 上是 nil** —— 不能用 `返回值:disable()`（真机直接报错）
- 因此实现为「开 = 逐个 `add_key_binding`，关 = 逐个 `remove_key_binding`」
- mpv 的 `msg.info` **不做 printf**，格式化必须显式 `string.format`（或用本文件的 `log()` 助手）

**我自己测试脚本翻的车（已加防护）**：`--msg-level=all=verbose` 是非法值 → mpv 直接退出；
把数组赋给 PowerShell 自动变量 `$args` → mpv 根本没启动。两次都把"工具失败"读成了"功能结论"。
→ 现在功能测试都有**前置断言**：先确认"脚本已加载"，否则判"本次测试无效"，不产出结论。

## 24. 1.2.0「交织」#6：导出不再堆积文件 + 面板匹配放宽

**问题**：每导出一次就在素材旁多出两个文件（csv + json）—— 时间戳进文件名导致的。
旁车 `<素材名>.marks.json` 本来就是单一固定文件，不是它。

**调查结论**（先查后改）：
- 两侧导出都用 `<素材名>_markers_<YYYYMMDD-HHMMSS>.csv` + 同名 `.json`（mpv 与面板同一套约定）
- 面板「自动找标记」的匹配写死 `stem + '_markers_'`（结尾下划线）→ 因此 **mpv 侧若先改默认名，面板会静默找不到**
- 所以次序必须是：**先放宽面板匹配 → 再改 mpv 默认名**

**改动**
- 面板：匹配放宽为 `stem + '_markers'`；候选排序改为**无戳优先**（无戳那份就是最近一次"覆盖式"导出），
  其余仍按名字倒序（时间戳词典序 = 时间序）
- mpv：`default_export_path(stamp)` 默认**无戳** → 每次覆盖同名文件；新增 `Ctrl+Shift+E`
  「导出标记（另存为迭代）」始终带戳；新配置 `export_stamp`（默认 false）与 `hide_export_json`（默认 true）
- 导出的同名 `.json` **默认设为隐藏**（减少目录里的视觉重复；`.csv` 保持可见）

**真机实证**（走 Lua 自带的 `script-message export` —— 无头环境里 `mp.input` 对话框弹不出来，
所以不走 `Ctrl+E` 那条路）
- 连续导出两次 → 目录里始终 **2 个**文件（csv 可见 + json 隐藏=True）→ 覆盖生效 ✅
- 日志路径确认无戳：`…\ref-CFR-23976-60min_markers.csv` ✅
- F1 帮助的折行日志里出现新动作行「导出并带时间戳（不覆盖，保留每一次的版本）」✅
