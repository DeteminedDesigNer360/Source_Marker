# 参考视频：量 Pr 与播放器之间的时间轴偏差

用 ffmpeg（2026-07-16 版）生成。目的只有一个 —— 回答：

> **Pr 和 mpv 对同一条素材的「时间」是否一致？如果不一致，是固定偏移，还是比例误差？**

先测准，再决定怎么补偿。别在没测之前把因子写死。

## 一、两个文件

| 文件 | 时长 | 帧数 | 帧率 | 用途 |
|---|---|---|---|---|
| `ref-CFR-23976-60min.mp4` | 01:00:10.02 | 86,554 | **恒定** 23.976（24000/1001） | 对照基准。恒定帧率下两边**理应完全一致** |
| `ref-VFR-60min.mp4` | 01:00:09.98 | 64,857 | **可变**：前半 23.976，后半每 2 帧取 1（平均 17.97，峰值 23.98） | 看 Pr 对 VFR 的「整合（conform）」是否与播放器一致 |

> **为什么基准用 23.976 而不是 29.97**：29.97 有丢帧 / 非丢帧时间码之分，**非丢帧时间码本来就会相对真实时间
> 每小时差 3.6 秒** —— 那是正确行为，不是 bug。拿它当基准会把「正常现象」和「真偏差」混在一起，
> 测出来的数没法解释。23.976 没有这个坑。
>
> 如果将来发现你的实际素材是 29.97，那我们**另外**再谈：那种情况下 3 s/h 很可能根本不是偏差，
> 而是 NDF 时间码的正常表现，补偿公式也是已知的（不是谜）。

## 六、实测结论（CFR，2026-10-06）

### 数据（帧号取自画面烧字 / Pr 的帧显示，与实测一致）

| 帧号 n | 真实 PTS（mpv） | Pr 时间码 | 偏差 |
|---|---|---|---|
| 0 | 0.0000 | 00:00:00:00 | 0.0000 |
| 240 | 10.0100 | 00:00:10:00 | −0.0100 |
| 21578 | 899.9824 | 00:14:59:02 | −0.8991 |
| 43157 | 1800.0065 | 00:29:58:05 | −1.7982 |
| 64735 | 2699.9890 | 00:44:57:07 | −2.6973 |
| 86314 | 3600.0131 | 00:59:56:10 | −3.5964 |

### 结论：根因是「24fps 时间码」，**不是 Pr 的 bug**

**Pr 的时间码 ≡ 帧号 ÷ 24，精确成立** —— 上表 6 个点、从 0 到 60 分钟，拟合残差恒为 `0.000E+000`。
mpv 显示的是**容器真实 PTS**（= 帧号 × 1001/24000），拟合残差 < 0.5 ms（就是毫秒取整）。

于是偏差恒为 `真实 × (−1/1001)`：

```
真实秒      = Pr时间码秒 × 1001/1000     ← 精确值，不是经验系数
Pr时间码秒  = 真实秒     × 1000/1001
```

60 分钟处偏差 **−3.596 s** —— 与最初的「3 s/h」完全吻合。

**这是 23.976 素材配 24fps 非丢帧时间码的标准行业惯例**（24p 素材传统上就带 24fps 时间码），
与 29.97 配非丢帧时间码属于同一类现象。**所以两边都不该"修"，要做的是换算。**

### 关键：两边在「帧号」上完全一致

「Pr 的时间码切换为帧之后，与画面的 n 是对应的」这句正是要害：

| | Pr | mpv |
|---|---|---|
| **帧号** | ✅ 正确 | ✅ 正确（`estimated-frame-number`） |
| **时间码 / 秒** | 24fps 时间码 | 真实 PTS |

**帧号是唯一跨宿主可靠的不变量；时间码不是。**

### 对「一键互跳」的直接结论

1. **不要传时间码字符串** —— 两边对同一串字符的解释不同，差 1/1001
2. **传帧号最稳**：两边帧号一致，各自用**自己的**帧率换算成自己的时间轴
3. 若只能传秒，必须带因子 `1001/1000`；该因子**可以自动算**，不必手工校准：
   `因子 = round(容器fps) / 容器fps`（用精确有理数 24000/1001 时就是精确的 1001/1000；
   若用 Pr 报的十进制 23.976，则 24/23.976 = 1.001001，差 1e-6，合 3.6 ms/小时 —— 可接受，但代码里最好用精确有理数）
4. Pr 的「属性」显示帧率 **23.976**（它知道真实帧率），但时间码仍按 **24** 走 ——
   **不要拿「Pr 显示的帧率」当作时间码的帧率**

### 还没测的

- **VFR 那份还没跑**：它回答的是另一个问题（Pr 对可变帧率的「整合 conform」是否与容器一致），
  与上面的速率问题互不覆盖。
- **一个 1 分钟就能补的小测试**：Pr 的 `Time.seconds`（面板内部用的就是它）是「真实秒」还是「24fps 秒」？
  在 Pr 里把播放头放到红色检查点（帧 21578），按 `I` 设入点，然后对比：
  - Pr 源监视器自己的时间码 → 已知 `00:14:59:02`
  - 面板「入」那一栏的时码（面板是用 `.seconds` × 23.976 自算的）

  面板显示 `00:14:59:23` → `.seconds` 是真实秒；显示 `00:14:59:02` → 是 24fps 秒。
  **这个结果决定互跳时因子该放在哪一侧。**

## 七、VFR 结论与统一模型（2026-10-06）

### 数据（用户实测）

| 标称 | Pr 时间码 | Pr 时间轴帧号 | mpv 显示 |
|---|---|---|---|
| 0 s | 00:00:00:00 | — | 00:00:00.000 |
| 10 s | 00:00:10:00 | 180 | 00:00:10.010 |
| 900 s | 00:14:58:05 | 16169 | 00:14:59.982 |
| 1800 s | 00:29:56:11 | 32339 | 00:30:00.007 |
| 2700 s | 00:44:54:16 | 48508 | 00:44:59.989 |
| 3600 s | 00:59:53:03 | 64677（原记 86314 为录入笔误，已修正） | 01:00:00.013 |

### mpv 侧「没变」是应该的

两个文件的检查点放在**同一批真实时刻**上（已用 `blackdetect` 复核）。VFR 改的是"帧怎么分布"，
不是"时刻在哪"，所以 mpv 读到的 PTS 必然一样。

### Pr 侧不是「没有规律」，规律很整齐

前四行精确满足（误差 0.0000）：

```
Pr 时间轴帧号 = 真实时刻 × 17.9659     ← 17.9659 = 64857 帧 ÷ 3610.013 s（容器平均帧率）
Pr 时间码秒   = Pr 帧号 ÷ 18           ← 18 = round(17.9659)
```

**Pr 做的是：把 VFR 按平均帧率 conform 成恒定帧率时间轴，再用「整数化后的帧率」写时间码** ——
与 CFR 那节的规则完全一致，只是帧率换成了平均值。

**所以"没有规律"的真正原因是：VFR 下 Pr 的时间轴帧号 ≠ 容器帧号**（CFR 时两者相等）。
不是 Pr 乱来，而是**「帧号」这个不变量在 VFR 下失效了**。

### 第 5 行原记的 86314：已确认为录入笔误

原记 `86314`（恰好是黄帧上**烧字的容器帧号**），正确值应为 `3600.0131 × 17.9659 ≈ **64677**`，
`÷ 18` → **`00:59:53:03`** ✓ 与所记时间码完全一致。
**用户已复核并修正为 64677 —— 模型在全部 6 行上成立。**

### 统一模型（CFR / VFR 同一套）

```
真实时刻 t  ← 容器 PTS ＝ mpv 的 time-pos ＝ Pr 的 Time.seconds    （唯一公共货币）
Pr 帧号     = t × 容器平均帧率
Pr 时间码   = Pr 帧号 ÷ round(容器平均帧率)
```

由此推出换算：`真实秒 = Pr时间码秒 × round(fps) / fps`

| 情形 | fps | 因子 = round(fps)/fps |
|---|---|---|
| CFR 23.976 | 23.976 | 24 / 23.976 = **1001/1000** = 1.001 |
| VFR（平均） | 17.966 | 18 / 17.966 = 1.00189 |

**形式完全一样，只有 fps 不同 —— 而 fps 是容器给的，所以因子永远可自动算，不需要手工校准。**

### 最重要的发现：`Time.seconds` 是【真实秒】

面板「入」显示 `00:14:59:02`（与 Pr 自己的时间码一致）。面板用的是
`_timecodeAt(item, seconds, sep)`，其 fps 取自 `item.getFootageInterpretation().frameRate`
—— 就是 Pr「属性」里显示的 **23.976**（不是 24）。代入：

| 假设 | 面板 `_timecodeAt` 输出 |
|---|---|
| `seconds = 899.9824`（真实容器 PTS） | **`00:14:59:02`** ✓ 与实测一致 |
| `seconds = 899.0833`（帧号 ÷ 24） | `00:14:58:04` ✗ |

**→ `Time.seconds` 返回真实秒，与容器 PTS 同一量纲。**

**（已由用户复核确认：面板 tcLine 自动输出的帧率是 `23.98fps` ——
即 `getFootageInterpretation().frameRate` = 23.976 而不是 24 —— 歧义正式关闭。）**

（面板时间码之所以与 Pr 显示一致，是因为 `_timecodeAt` 内部用 `round(fps)` 拆位 ——
它本来就是按 24p 时间码惯例写的。）

### 对「一键互跳」的最终结论

1. **Pr 的 `.seconds` 与 mpv 的 `time-pos` 是同一种货币（真实秒）** —— 直接传秒**不需要任何因子**
   - Pr → mpv：`--start = <源监视器位置的 .seconds>`
   - mpv → Pr：把 `time-pos` 当秒用
2. **「3 s/h」只在人眼读时间码时出现** —— 那是显示层换算，不是数据层偏差
   - 纪律：**不要传时间码字符串**，只传秒（或帧号 + 容器 fps 换算）
3. **帧号在 CFR 下是可靠不变量，在 VFR 下不是** —— 用帧号就必须配容器 fps
4. VFR 下 Pr 时间轴帧号 = `t × avg_fps` ≠ 容器帧号 —— conform 的正常结果，不是 bug

> **互跳既不需要"校准"，也不需要记偏移量。** 唯一要守的纪律：走 `.seconds` / `time-pos`，
> 不走人眼看到的时间码。
