## 二、待修问题

### P1（重大问题）概览条环贴住端点时，时间轴不是 0 / 全长 —— 长素材映射误差

> **✅ 已修（2026-11-07，`9c56006`）—— 但过程走了三步，本段下面「改法确定为 a（位置线性）」那条判错了**
>
> | 轮次 | 改了什么 | 结果 |
> |---|---|---|
> | r49 | 位置**和**宽度都改成线性（照 Pr 的**入出点标记**）| ❌ 对错了物体：概览条对标的是 Pr 的**可见范围滑块**，宽度是幂律 |
> | r50 | 宽度改回 `w = u^p`（p 由「最小跨度正好 22 逻辑 px」反推）| ✅ 宽度定稿 |
> | r54 | 中心补回 `k = (1−w)/(1−u)` | ✅ 位置定稿，盲区归零 |
>
> 本段保留原判断过程作历史记录；**最终解见本节末尾「✅ 已修」**，以及 `docs\测量总账-r47至今.md` §2.8。
**现象**（清单 D 段末，第 352 行原文）：

> **重大问题**：控制条位置在长素材中具有**非常大**的映射误差！控制条环到达轨道端点时，端点一侧的时间轴应该是 0s 和 1h.
> 而现在却可能是 6min 和 58min！这个误差还会随着缩放程度的增大而增加，需要测量。

- **复现**：1 小时素材，把区间调到接近全片（例如 6 min ~ 58 min）→ 概览条亮段看起来已接近满宽、两环贴近条两端，
  但主区时间轴两端是 `00:06:00:00` 与 `00:58:xx:xx`，不是 `00:00:00:00` / `01:00:10:01`。跨度越小误差越明显。
- **影响**：概览条不能用来判断「区间在片子的哪一段」，只能看个大概。拖环靠同一套反解（自洽）所以**拖得动**，但「视觉位置 = 时间」这条直觉失效。
- **初步定位（未验证）**：r47 第六步把条宽改成幂律 `w = u^pow`、`pow = ln(W/rw)/ln(minspan/dur)`（`TL.bar_pow` 反推，`:2968-2979`；`bar_geom` `:2994`）。
  - 1 h 素材 `pow ≈ 0.476`：`u=0.87`（6~58 min）⇒ `w = 0.87^0.476 ≈ 0.936` ⇒ 视觉上几乎是满条。**这是饱和**，u 从 0.87 到 1.0 肉眼无法区分。
  - 再叠加 `bar_geom` 里 `c = 0.5 + (mid−0.5)/k(u)` 与 `l = c − w/2`，`l < 0` 时被钳到 0（贴片头）⇒ 左端直接跳到条最左，进一步放大错觉。
  - `tl_ov_k = 1.19` 是**短片**拟合值；Pr 60 min 实测 k 是 0.52~0.96 且随 u 变化（`docs/测量-Pr控制条数学与mpv实现.md` §3），长片位置还会额外偏。
- **与 Pr 的关系（2026-10-25 已实测，结论推翻原猜测）**：**Pr 的入出点条完全线性、不饱和、没有最小宽度**。
  - 5 min 素材（9000 帧 / 条宽 1240 px）：`x = 14 + 0.1384·t`，0~900→138、2250~6750→948、8880~8999→1260、4500~4530→640.5，**残差 ≤1 px**；
  - 15 min 素材（27000 帧）：`x = 11.7 + 0.04626·t`，0~13500→636、2250~6750→324、seek 20000→937；
  - **31 帧差 4.3 px 也分成两条蓝标记** ⇒ Pr 不撑开、不设最小宽度、也不做幂律。
  - 之前记的「Pr 60 min 也饱和（`u=0.7755 → w=0.8878`）」是**误读**：那是 ruler 下方的**可见范围滚动条**（深色细条 + 两个圆环 = 可视窗口左右边界，拖它区间帧数纹丝不动），
    不是入出点条。**Pr 的入出点画在 ruler 上，是蓝色标记。**
  - ⇒ **改法确定为 a（位置线性）**，幂律 `w = u^pow` 整个删掉。
- **修前需要测**：~~Pr 六档~~（已完成，见下）；剩 ① 我方同档对照画偏差曲线；② `tl_ov_k` 常数（**线性化后 `tl_ov_k` / `TL.bar_pow` / `bar_geom` 里的 k(u) 全部作废，一并删除**）。
- **落地口径（照 Pr + 一处有意偏离）**：
  - **位置线性**：`l = x0 + (x1-x0)·t0/dur`、`r = x0 + (x1-x0)·t1/dur` ⇒ **环贴条端 ⇔ 时间贴片头/片尾**成立；
  - **宽度**：`w = (x1-x0)·span/dur`，若小于最小可见宽度（`tl_ov_min_px`）则**以区间中心为锚撑开**到最小宽度；
  - **有意偏离 Pr 的原因**：Pr 的概览条不是主要交互控件（短区间靠 ruler 上的蓝标记看），mpv 的概览条要**点击跳转 + 拖环**，不撑开就点不中；
  - 撑开时**只有视觉被拉伸，反解仍按真实时间** ⇒ 拖动时环心对应的时间会有一点点偏差，接受（Pr 无此问题因为它根本不撑开）。


**✅ 已修（r49 → r50 → r54，2026-11-07 收口）**

1. **r49 判错了对标物**：把概览条当成 Pr ruler 上的**入出点标记**（那个严格线性、不撑开），于是位置与宽度都改线性，结果是高缩放档亮段缩到 0、中间横轴拖不动。
2. **r50 宽度改回幂律**：概览条真正对标的是 Pr 的**可见范围滑块**（`⚪====⚪` `docs\待修问题` 上面那段 Pr 实测也是它）。`w = u^p`，`p = ln(W_min/rw) / ln(minspan/dur)`。
3. **r54 中心补回 k**：Pr 的中心不是线性 `xc = c`，而是 `xc = 0.5 + (c−0.5)·k`，且 `k` 有闭式解 **`k = (1−w)/(1−u)`** —— 它的作用正是「让区间贴片头时环正好贴轨道左端」。
   - 三片长九个点全部吻合（30 s / 30 min / 60 min，误差 ≤0.007），见 `docs\测量总账-r47至今.md` §2.8。
   - 代码落在 `TL.bar_k`（`source-marker-united-1.2.0-alpha-r58/mpv-player/portable_config/scripts/source-markers.lua:3316`，两参 `(u, dur)`）、`TL.bar_geom`（`:3369` / `:3378`）、`TL.bar_solve_px`（`:3480`，反解用同一 k，保证绘制与拖动同源）。
   - **连带归零**：§15.6「贴边平移条不跟手」（60 min 素材 u=0.3 时盲区 416 s）→ 0；r50 §4.3.2「碰右端偏 13%~21% 轨宽 = 162~264 px」→ 0。
### P2（重大问题）抓左环向右拖，进同动那一刻右环先向左瞬移、之后才向右

**现象**（清单 D 段，第 343–345 行原文）：

> 这个问题**很大**，现在左环会在播放头达到 p=0.5 时，缩小与放大方向反转。也就是从全片开始激活左环鼠标一直向右移动，
> 右环会出现先向左后向右的情况。这里的是非曲直也是难以论说，等待测量定论。

- **复现**：全片区间、播放头不在正中（例如 10 s / 30 s），抓**左环**后鼠标**持续向右**移动。
  单动段左端右移、右端钉死；当左端靠近播放头、`pn` 落到 0.5±0.02 时进入同动 ⇒ **右端瞬间向左甩**，继续拖才向右。
- **影响**：端点在切换点发生大跳（不是小跳），属于手感硬伤，且和 r47 第十步「速度统一」的初衷相反。
- **初步定位（未验证）**：`tl_grab_move`（`:3204`）进入同动的第一帧用「跨度保持 + 中点点到播放头」重构区间 ——
  `gr.sym_l0, gr.sym_r0 = tph - sp_cur/2, tph + sp_cur/2`（`:3321`），`sp_cur = min(g.t1-g.t0, hi)`（`:3315`）。
  但单动阶段被钉死的远端是 `gr.r0`（可能在 `dur`），重构后远端变成 `tph + sp_cur/2`（很小）⇒ 右端从 `dur` 跳到播放头附近。
  进入同动后继续右移：`lend = (gr.sym_l0 or …) - d`（`:3349`）、`sp = 2*(tph - lend)`（`:3351`）⇒ 端点向外扩，方向与单动段的「缩小」相反。
- **修前需要测**：`--script-opts=source-markers-tl_dbg=file` 跑一次完整行程，用 `tools/analyze-dbg.py` 看 `tl-grab` / `tl-drag-n` 系列里
  进入同动那一帧前后 `g.t0/g.t1` 的跳变（预期能看到右端 `dur → tph+sp/2`）；再决定：
  - ① 进入同动时**保住被钉死的那一端**（只把另一端拉到对称位置，跨度随之变）；
  - ② 或把进入条件收紧成「跨度已触底 `minspan`」才进同动（r46 第十九轮曾用过），pn 窗口只做辅助；
  - ③ 或切同动时按 `gr.edge_lock` 的方向选择先动哪一端。
  这三种都要先知道 **Pr 在同样操作下怎么表现**，否则改完仍无参照。

- **✅ 已修（r52，`913e5e0`，2026-10-31）** —— 根因**不是**上面猜的「丢掉被钉死的远端」。用新建的取证探针 `tools\probes\tl-sym.lua`（三场景，`tl-grab` / `tl-drag-n` 直接驱动拖圆逻辑）拿到逐帧 `pn / sym / 端点` 后定位到两处参数：
  - **① `EPS = 0.02` 太宽**（`source-markers.lua:3546`）：`in_win = |pn-0.5| <= EPS` 让 pn=0.481 就进同动，而 pn<0.5 ⇒ 跨度 = hi/(2pn) > hi ⇒ `sp_cur = min(跨度, hi)` 被钳掉 ⇒ 跳幅 ≈ 2·EPS·hi（最多 4% 跨度）。实测 0~30@10 抓左圆：`0,20.791` 一帧变 `0,20.000`，跳 **0.791 s**。收窄到 **0.002** 后同样场景只跳 **0.028 s**（0.14%）。
  - **② 抓左圆时方向反了**（`source-markers.lua:3668`）：`lend = (gr.sym_l0 or (tph - hi/2)) - d`，`d = (target-m0)*C*dur` 随鼠标右移为正 ⇒ 左端左移 ⇒ 立刻撞片头 ⇒ 走「撞边外扩」分支 `sp = 2*tph - lend` ⇒ **抓左圆向右拖（缩小）反而越拖越大**（实测 20.000 → 20.835）。改成 `+ d` 后跨度单调减小（30.000 → 29.791 → … → 19.769）。
  - **跨过 pn=0.5 的路径实测零跳**：跨过时 pn≥0.5 ⇒ 跨度≤hi ⇒ `min` 不生效（场景 3 实测 `0,39.958` → `0.021,39.979`，跨度 39.96 不变）。
  - C 组那 4 条（最窄档抓右环 / 抓左环 / 拖到顶整体平移 / 长素材全程拖）现在可以一起测了。

### P3 时间轴（刻度带）上的滚轮语义与 Pr 不一致

**现象**（清单 B 段，第 312–317 行原文）：

> 当前状态下在"时间轴"上时：单纯滚轮等于前后挪单帧，Ctrl+滚轮和 Shift+滚轮的效果和在"控制条"上的时候一样分别是精细缩放和粗缩放，
> 这个有点问题，对应 Pr 在"时间轴"上的动作应该是 **Shift+滚轮 = 前后挪 5 帧，Ctrl+滚轮 = 单纯滚轮**。
> 在"控制条"上的 Alt+滚轮和 Shift+Alt+滚轮在功能实现上是没有问题的。
> **重要提示**：当前的步长应该还是基于最初的"手感"方法确定的，可能存在误差，需后来进一步测定。
>
> **2026-10-26 已测定**：Pr 滚轮是**固定像素步长**（裸滚 2 px/格、Shift 10 px/格、Alt 平移 1 px/格、Alt+Shift 平移 5 px/格），与当前缩放级别无关；且**缩放锚点 = 播放头**，贴边时上下速率会变成 1:2。详见 `docs\测量-Pr概览条真机实测-2026-10-25.md` §五、§六。

| 区域 | 当前行为 | Pr 期望 |
|---|---|---|
| 时间轴（刻度带）· 单纯滚轮 | 前后挪 **1 帧** | 保持 |
| 时间轴 · `Ctrl+滚轮` | **精细缩放**（与控制条相同） | **等于单纯滚轮**（挪 1 帧） |
| 时间轴 · `Shift+滚轮` | **粗缩放**（与控制条相同） | **前后挪 5 帧** |
| 控制条（概览条）· 单纯滚轮 | 缩放 | 保持 |
| 控制条 · `Ctrl` / `Shift` | 精细 / 粗缩放 | 保持 |
| 控制条 · `Alt` / `Shift+Alt` | 平移 ±1 px/格 / 平移 ±5 px/格 | 正确，保持（Pr 实测：`Alt` = 平移模式，`Shift` = 5 倍速） |

- **初步定位（已确认，不是猜测）**：`Ctrl+wheel` / `Shift+wheel` 是**全局绑定**，根本不看区域 ——
  `tl_bind_wheel('Ctrl+wheel_up', function() tl_zoom(TL_STEP.ctrl, …) end)` 等四行在 `:2896-2899`；
  只有单纯 `wheel_up/down`（`:2894-2895`）才进 `tl_wheel(dir)`（`:2882-2893`）按 `tl_wheel_region`（`:2804-2811`，返回 `'axis'` / `'con'` / nil）分派。
- **✅ 已修（r53，2026-11-01）**：按下面这个改法落地。新增 `tl_wheel_mod(dir, kind)` 先问 `tl_wheel_region`，`axis` 走单帧（Ctrl 1 帧 / Shift 5 帧），其余走 `tl_zoom`；`tl_wheel_frame` 加 `steps` 参数；取证钩子 `tl-wheel-at` 加第 4 个 `mod` 参数。离线实测：刻度带裸滚 ∓1 帧、Ctrl ∓1 帧、Shift ∓5 帧，概览条三档缩放步长各不相同（未回归）。
- **改法（原记录，已按此实施）**：把 `Ctrl` / `Shift` 的四条绑定也改成走区域分派 ——
  `axis` + Ctrl ⇒ `tl_wheel_frame(-dir, 1)`；`axis` + Shift ⇒ `tl_wheel_frame(-dir, 5)`；
  `con` + Ctrl/Shift ⇒ 现有精细/粗缩放。需要给 `tl_wheel_frame`（`:2872-2881`）加步数参数（现在写死 ±1 帧）。
- **附带待办（NS1，2026-10-26 已测定）**：步长 `tl_zoom_steps='1.003,1.001,1.01'`（`:86`，被 `:2656-2658` 读进 `TL_STEP`）是**比例**步长，而 Pr 是**固定像素**（裸滚 2 px/格、Shift 10 px/格）⇒ 应改成 `V/rw × 常数`。详见 `docs\测量-Pr概览条真机实测-2026-10-25.md` §五、§九.2。
  注意 `TL_STEP` 初值 `1.10/1.03/1.35`（`:2653`）只是兜底，实际生效的是配置里的 1.003/1.001/1.01。

### P4 概览条最小档宽度：长素材 / 改窗口后不是 27 px

**现象**（清单 E 段，第 360–361 行）：

> - [ ] 拉宽 / 缩窄窗口后再缩到最小 → 仍是 27 px（宽度指数按画布宽反推）//**在长素材中明显更短！**
> - [ ] 宽度曲线单调：1 h 全片满宽 → 600 s / 100 s / 20 s / 5 s 逐档变窄，无跳变   ← **未通过**

- **影响**：最小档可能细到点不中（环径 13 px + 横条 13 px 是 r47 专门调过的）；宽度曲线不单调时拖动会出现「手在动、环不动」。
- **初步定位（未验证）**：
  - `tl_ov_min_px = 27`（`:95`）定义为「两环**环心距**」，而 `bar_pow` 反推用的 `W = tl_ov_min_px`（`:2979`）当作亮段目标宽度 ⇒**环心距 vs 外沿距差 13 px**（环径），量法与实现不一致；
  - 实际绘制下限走 `ov_min_px`（`:2424-2426`，取 `2*cr+2` 与 `tl_ov_min_px` 的较大者），与 `bar_geom` 的钳制是两处独立逻辑，窗口变化时 `pow` 变、钳制不变 ⇒ 可能互相打架；
  - 长素材 `pow` 小（0.476），窄窗口下 `w` 更容易被钳到下限 ⇒ 视觉更短。
- **修前需要测**：1 h 与 30 s 素材各量一次最小档的**两环外沿距**与**环心距**，窗口 1280 / 1920 / 960 三档各一次。

### P7（高分屏）面板与概览条的尺寸在 dpi 1.75 下不跟随 —— 2026-10-27 实测

**实测环境**：2560×1600 物理 / **dpi 1.75** / 逻辑 1463×914。用 `_tmp\probe-osd.lua` + `_tmp\probe-metrics.lua` 探针直接问 mpv 拿值。

### P9（视觉）轨道比 Pr 短 2×cr，全片时环「溢」出槽外 —— 2026-11-01 立项

**现象**：全片时两个**环心**贴在轨道两端（`wx0 = x0`、`wx1 = x0 + rw`），环本身**凸出轨道外 `cr` px**，所以「轨道长度 ≠ 概览条最大外沿距」。1280×800 实测：轨道 `20..1260`（长 1240），环心 `20.8 / 1259.5`，环外沿 `17.8 / 1262.5` —— **外沿距 1244.8 > 轨道 1240**。Pr 那边两者**相等**：槽正好兜住环的外沿。

**为什么值得改**：我们一直在对齐 Pr 的概览条。「外沿距 / 环心距」是两套口径（换算见 `docs\术语标准-元素与操作.md` §1.1），但**视觉上**槽短一截，看起来像环溢出来 —— 这是唯一一处和 Pr 的直观印象对不上的地方。

**修法（纯视觉，不动任何测量与映射）**

| 位置 | 现在 | 改成 |
|---|---|---|
| 轨道绘制（`source-markers.lua:2627-2629` 一带的 `x0` / `rw`）| `x0 .. x0 + rw` | `x0 - cr .. x0 + rw + cr` |
| 概览条的点击 / 拖动命中 | `x0 .. x0 + rw` | 同步外扩 `cr`（否则最外 `cr` px 是死区，抓不到）|

**明确不动的**：`rw`、`tl_ov_min_px`、`wx0` / `wx1`、幂律 `p`、`TL.bar_geom` / `TL.bar_solve_px`、全部历史测量数据。环心行程仍是 `x0 .. x0 + rw`。

**前置校验（已算过，三档都够）**：轨道两端到面板边缘还有 `pad = max(4, floor(9*scale+0.5))`（`source-markers.lua:2446`）—— 800p 是 7 > `cr` 3 ✓；1080p 是 9 > `cr` 4 ✓；1600p 是 13 > `cr` 5 ✓。外扩后不会顶到面板边缘。

**验收**：① 全片时轨道两端正好被环外沿覆盖，无空隙无溢出；② 最窄档外观不变；③ 拖到最左 / 最右仍能抓起（死区测试）；④ 800p / 1600p 两档都看一遍。

**✅ 已修（r55，2026-11-07）** —— 与上面写的有两处偏差，都已处理：

- `ov_ext` 取 **`math.max(2, math.min(crv, pad - 1))`**，不是裸 `crv`。原因：800p 下 `pad = 5`、`crv = 4`，直接外扩 `crv+1` 会让槽贴死面板边缘（看不到概览条块自己的左框），夹 `pad-1` 保证至少 1 px 余量。
- 滚轮区域判定 `tl_wheel_region` 的 x 容差从 `±2` 放宽到 `±(2 + crv)`，否则槽新外扩出来的最外几 px 是死区。

实测（1000×700，5 min 素材，`rw = 820`）：环心 89.5 / 909.5 与环外沿 83..96 / 903..916 **均未变**；槽外沿从 `86..913` 变成 **`83..916`**，与环外沿逐像素重合。离线映射断言九档仍 PASS。

### P10（缺陷）拖环越过条右端那一帧，左端倒退 703 s —— 2026-11-08 发现

**现象**：60 min 素材、可见范围缩到最窄（两环心距 22 px）、播放头在 50 min（区间外），鼠标压住右环往右拖：

| 帧 | 鼠标 x | 区间 | 跨度 |
|---|---|---|---|
| 95 | 1166 | 1682.90 ~ 3604.14 | 1921.24 s |
| 96 | 1174 | **979.60** ~ 3610.02 | **2630.42 s** |

撞到片尾那一帧**左端从 1682.90 倒退到 979.60（−703.3 s）、跨度从 1921 跳到 2630（+37%）**，之后鼠标继续拖出条外 111 px 完全不动。

**根因**：`source-markers.lua:3840-3846` 的贴片尾分支写的是

```lua
local lpos = (kind_eff == 'left') and target_eff or anchor
w = 1 - lpos
```

抓右端时 `lpos = anchor`（**抓起那一刻**的左端像素 `gr.l0 = 0.271360`），与鼠标拖到哪无关 ⇒ 跨度恒等于 `(1 − 0.271360) × 3610.023 = 2630.42 s`。鼠标位置在这一支里被完全丢弃。

**用户期望**（2026-11-08）：「理论上右环到达轨道边界之后，继续向右动鼠标，左环会一直向左（可见范围继续扩大），但当前鼠标映射下，鼠标在右环到达轨道边界之前，就碰到屏幕边缘无法移动了。」

**为什么不是改一行就能到全片**：60 min 素材轨道 1055 px，撞边时鼠标 x=1166、屏幕右边缘 1280，只剩 114 px。按 1:1 增益只能把跨度从 1921 推到约 2331 s（全片 3610）。**要到全片需要「鼠标超界量 × 增益」的新驱动机制**，增益口径未定 ⇒ 单独立项，未排期。

**最小修复（只消掉倒退）**：撞边那一帧的跨度改用「撞边那一刻的跨度」而不是 `anchor` 快照，撞边后整段停住。改动只在 `:3840-3846` 一处。

**验收**：① 从最窄拖到光标撞屏幕边缘，左端时间**全程单调**（不回退）；② 跨度单调不减；③ 鼠标拖出条外时要么停住、要么继续长，不能跳。

### P11（缺陷）同动段撞片头/片尾，跨度跳成「右端时间」而不是对称上限 —— 2026-11-08 定位

**现象**（用户原话）：「30s 素材播放头 @20s，拖右环使得可见范围增大，当右环到达轨道边界的一瞬间，左环就会瞬移至轨道左端，使得可见范围变为全片。」

| 12 | 17 ~ 21（播放头**在**区间内） | 20 | → **30.000**，区间 `0.000,30.000` | **+50.1%** |

| 10 | 0 ~ 10（播放头**在区间外**） | 20 | 29.931 → 30.000 | 平滑 |

⇒ **判据是「播放头在不在可见范围内」**：在范围内走同动段（`sym`），撞边后跳成全片；在范围外走 `bar_solve_px`，平滑（那条是另一回事，见 P10）。

**根因（三段）**

1. `source-markers.lua:3761` 撞片尾把**右端时间**当成了**跨度**：

```lua
local rend = (gr.sym_r0 or rmax) + d      -- 右端时间（秒）
if rend <= rmax + 1e-9 then
    sp, lock = 2 * (rend - tph), nil
else
    sp = rend                              -- ← 撞边这一支：应是 hi，写成了 rend
end
```

`hi = min(2*tph, 2*(dur - tph))`（`:3723`）是同动的对称上限；撞片尾时 `hi = 2*(dur - tph)`。而 `rend` 在撞边时已超过 `rmax = tph + hi/2`，即 `rend > dur` ⇒ `sp > dur`。

2. `:3768` 撞片头同形：`sp = 2 * tph - lend`，`lend` 是左端时间（负数）⇒ `sp > 2*tph = hi`。

3. `:3772` `sym = math.max(minspan, math.min(g.dur, sp))` 把超上限的跨度钳到片长，`:3855` 的 `edge_lock == 'tail'` 分支再给出 `n0, n1 = max(0, dur - sym), dur` ⇒ **`[0, 30]` 全片**。

**为什么是历史遗留**：`:3761` 的注释写的是「撞边：那一端钉死，右端继续按同一速度外扩」—— 意图是「右端按同一速度继续走」，但代码把「右端的**位置**」直接赋给了「跨度」。播放头恰在正中（`tph = dur/2`）时位置 ≈ 跨度，看不出问题；只有播放头偏离中心时两者才分道扬镳。

**修法（两行）**：撞边后跨度取对称上限 `hi`。

```lua
-- :3758-3761 撞片尾
if rend <= rmax + 1e-9 then sp, lock = 2 * (rend - tph), nil else sp = hi end
-- :3765-3768 撞片头
if lend >= -1e-9 then sp, lock = 2 * (tph - lend), nil else sp = hi end
```

**为什么与连续分支严格衔接**：`rend = rmax` 时连续分支给 `2*(rmax - tph) = 2*(hi/2) = hi` —— 与撞边分支同值，交界处零跳变。撞片头同理。

**验收**：① 场景 11 / 12 撞片尾停在 `[10, 30]`（跨度 20），不再变全片；② 场景 10 / 13（播放头在区间外）行为不变；③ 撞片头对称（播放头 @10、初始 `[8, 12]` 应停在 `[0, 20]`）；④ 撞边后继续拖，跨度不再变。

**与 P10 的关系**：两条都在「撞边」这一族，触发条件不同 —— P10 是播放头**在区间外**（`bar_solve_px` 的 `:3840` 分支用 `anchor` 快照），P11 是播放头**在区间内**（同动段 `sp = rend`）。修一条不会顺带修掉另一条。

### P12（缺陷）同动段拖环速度随跨度变化 —— `C = 0.6` 是线性模型时代的常数 —— 2026-11-08 定位

**现象**：同动段（播放头在区间中点、两环对称缩放）里，鼠标走同样多像素，跨度变化量随当前跨度变化。跨度越小越跟手，跨度越大越迟钝。60 min 素材（`p = 0.5040`）：

| u（跨度/片长） | 对应跨度 | w = u^p | k | 实际速率（1:1 记 1.0） |
|---|---|---|---|---|
| 0.00046 | 1.67 s（最窄） | 0.0219 | 0.979 | **0.587** |
| 0.028 | 100 s | 0.1640 | 0.860 | 0.516 |
| 0.1 | 6 min | 0.3134 | 0.763 | 0.458 |
| 0.5 | 30 min | 0.7051 | 0.590 | 0.354 |
| 0.9 | 54 min | 0.9483 | 0.517 | **0.310** |

最窄档与接近全片差近 2 倍。

**根因**：`source-markers.lua:3752` 的 `local d = (target - m0) * C * g.dur`（`C = 0.6`）。`target - m0` 是**条上位置差**，乘以 `dur` 就当成了秒 —— 隐含 `k ≡ 1`。而 `bar` 映射下条上位置是压缩的（`xc = 0.5 + (c−0.5)k`，`:3413` / `:3422`），正确换算是 `d = (target − m0) * C * dur / k`。

**来历（提交史）**：

| 时间 | 提交 | 事实 |
|---|---|---|
| r46 | `24c8cb6` | `bar` 映射引入，`k` 是**常数 1.1886**（「宽度 u^1.30 + 中心线性 k=1.1886」） |
| r47 第十步 | `b7c9faf` | `C = 0.6` 定标，目的是消「撞边速度翻倍」（对称段 0.60 / 撞边 1.20） |
| r50 / r54 | — | `k` 改成 `(1−w)/(1−u)`（`TL.bar_k`，`:3360`），随 `u` 变化，范围 0.5~1 |

⇒ `C` 标定时 `k` 是常数，现在是变量，**从 r54 起两者不同源**。r47 标定时的实际速率是恒定的 `0.6 × 1.1886 = 0.713`，处处一致。

**为什么以前没发现**：`k` 只在 `u` 接近 1 时才明显偏离 1（`u = 0.00046` 时 `k = 0.979`），而日常拖环多在小区间上做；到 30 min 跨度时已经慢了一半。

**与上机批注的关系**：`上机测试清单-1.2.0.md:376` 用户写「缩放速度已低于鼠标移速，多数情况鼠标先到窗口边缘」。当时归因为「同动 0.6 的速度台阶是设计」，实际成因是 `0.6` 乘上了一个从 1.19 掉到 0.5 的 `k`。

**修法（未实施）**：`d = (target − m0) * C * dur / TL.bar_k(u, dur)`，并**重新标定 `C`** —— 0.6 这个值里含着旧 `k = 1.1886`，直接除新 `k` 会让同动段变快 1.7 倍（0.713 是当时的恒定值，若要维持它，新的 `C ≈ 0.713`）。

**验收**：① 同一素材上 `u ≈ 0.0005` 与 `u ≈ 0.028` 两组，每步 `Δ跨度 / 鼠标 px` 比值应相等（现状应差 1.15 倍，修后为 1.00）；② 手感与 r47 标定时一致（速率 0.713 恒定），需用户上机确认。

**附带订正（同一轮，2026-11-08 再订正）**：此前口头说法「同动时两环同速且跟鼠标」**描述的是 Pr，不是 mpv**（用户 m17039 澄清）。
- Pr：宽度变化恒 2 × 鼠标位移、对称 ⇒ 每环 1× 鼠标，与播放头无关。
- mpv 同动段：`Δl = Δxc − Δw/2`、`Δr = Δxc + Δw/2`、`Δxc = (c−0.5)Δk`，环速随跨度从 **0.49× 变到 6.92×**（60 min 实测：1.67 s 档 6.92×、100 s 档 2.20×、1800 s 档 0.49×）。
- mpv 单动段：实测 **0.66×**（60 min、跨度 610 s），真机报 1.6:1（0.625×）。
⇒ 「1.14×」是 30 min 素材 100 s 档的推算值，**不是通例**，已从结论里撤下。

**与 P10 / P11 的关系**：三条都在拖环路径上但互不重叠 —— P10 在 `bar_solve_px` 的越界分支、P11 在同动段撞边分支、P12 在同动段的连续分支。

**r49 为什么错**：我把概览条对标成了 Pr 的**入出点标记**（ruler 上那两条蓝线，完全线性），于是把宽度也改成 `u`。
用户 m10404 纠正：mpv 里对应入出点的是时间轴上那对**中括号**（AB 循环），概览条对标的是 **Pr 的可见范围滑块**，长度本来就非线性。
r49 的两条症状都由此而来：

| 症状 | 机制 |
|---|---|
| 长素材全片附近条几乎满宽、短素材高缩放等级下「区间还在缩但条不动」 | 线性下 `w = u`，30 min 的 40 帧只有 0.92 px，靠绘制侧硬撑到 22 px，撑开量 24 倍 |
| 最窄档中间横轴拖不动 | 同上，视觉宽 22 px 全由钳制产生，`w` 随时间的变化被钳平 |

**r50 定稿**（相对 r47 只差两处，宽度幂律本来就是对的）：

```
w  = u ^ p                        p = ln(W_min/rw) / ln(minspan/dur)
xc = c                            (t0+t1)/(2*dur)        ← 删掉了 k(u) 横向放大
W_min = 22 × display-hidpi-scale  （tl_ov_min_px=0 时自动）
```

- `p` 让 **u = minspan/dur 时 w 恰好等于 W_min/rw**，最小档是真实映射，不再靠视觉硬撑。
- `p` 可以 >1（短素材，条更窄）也可以 <1（长素材，条更宽），方向由几何决定，不做人为夹取。
- 代码落点：`TL.bar_pow(dur)` 真实现（rw 取 `TL.rw`）、`TL.bar_geom` 的 `w = u ^ TL.bar_pow(dur)`、
  `TL.bar_solve_px` 的 `u = w ^ (1/p)`、拖动侧 `wmin = max(W_min/rw, (minspan/dur)^p)`。

**离线验证**（窗口 1000×700 ⇒ rw=820，七档全命中模型，误差 ≤1 px）：

| 素材 | p | 档位 | wx0/wx1 | 期望 |
|---|---|---|---|---|
| 5 min | 0.668 | 0~0.5 | 90 / 606 | 90.0 / 606.1 |
| 5 min | 0.668 | 0.25~0.75 | 241 / 758 | 242.0 / 758.0 |
| 30 s | 1.162 | 0~0.5 | 90 / 456 | 90.0 / 456.4 |
| 30 min | 0.502 | 0~0.5 | 90 / 669 | 90.0 / 669.0 |
| 30 min | 0.502 | 0.25~0.75 | 210 / 789 | 210.5 / 789.5 |

- 拖右环（75~225 拖 720/740/760）：左端环心恒 241，右端逐像素跟手。
- 最窄档（1.2 s）：画成 22 px，抓右环拖动左端像素不动。
- 闸门 `run-all-tests.ps1` EXIT=0。

**必须接受的取舍（P1 的原始现象会回来一小部分）**：幂律下 `w > u`（长素材），小跨度时 `l = c - w/2` 容易 < 0 被钳 ——
**环贴在端点上，但那一端的时间不是 0/全长**。Pr 的可视滑块本身就是这样（30 min 实测碰右端时位置偏 13%~21% 轨宽 = 162~264 px），
它准的只有宽度。用户 m10437 的四条要求已把优先级排死：位置线性（平移跟手、撞端点即片头片尾）> 宽度幂律（极小区间也点得中）。

> **⚠️ 这条取舍已被 §4.3.3 取消（2026-11-07）**：Pr 的中心不是线性，而是 `k = (1−w)/(1−u)` 的压缩中心，补上它之后「环贴端点 ⟺ 时间贴片头/片尾」两端同时精确，偏差从 162~264 px 降到 0。宽度 `w = u^p` 不必动。

### 4.3.3 B1：k 的闭式解 —— r50 那个「必须接受的取舍」可以取消（2026-11-07）

> 数据与归因见 `docs\测量总账-r47至今.md` §2.8；实施记录见 `source-marker-united-1.2.0-alpha-r58\改动说明.md`「第 9 条 B1」。

**结论**：Pr 可见范围滑块的中心不是线性，是**压缩中心**：

```
xc = 0.5 + (c − 0.5) · k ,   k = (1 − w) / (1 − u)
```

这是「贴片头 ⟺ 条贴左端」与「贴片尾 ⟺ 条贴右端」两条件的**同一个解析解**，两端同时精确、零偏差。

**四个新样本 + 五个历史点全部吻合（误差 ≤ 0.007）**：30 min 素材上 S1/S2（u=0.5，两个不同 c）给 k=0.598/0.600，公式 0.5989；S3/S4（u=0.25）给 0.678/0.680，公式 0.6801。K=1 的预测则偏 60~149 px。

**这直接推翻 §4.3.2 末段那条取舍**：

| §4.3.2 原文 | 补 k 之后 |
|---|---|
| 「环贴在端点上，但那一端的时间不是 0/全长」 | 环贴端点 ⟺ 时间贴片头/片尾，两端同时精确 |
| 「碰右端时位置偏 13%~21% 轨宽 = 162~264 px」 | 偏差 0 |
| `docs\设计-第9条-时间轴与面板.md` §15.6 的盲区表（60 min u=0.3 时 416 s，占跨度 39%）| **整条消失** |

**宽度不动**：r50 的 `w = u^p` 是对的（p 让最小档是真实映射而不是视觉硬撑），r49 的线性化才是方向错的。

**改动清单（待确认后开工）**：

| 位置 | 现在 | 改成 |
|---|---|---|
| `TL.bar_k`（`source-markers.lua:3307`）| `return 1` | `(1 − w)/(1 − u)`，`u → 1` 取极限 `p` |
| `TL.bar_solve_px`（`:3370`）| `c = (a+b)/2` | `c = 0.5 + ((a+b)/2 − 0.5)/k`（绘制与反解必须同源，否则 P4 的老毛病复现）|
| `TL.bar_geom` 贴边三支 | 硬编码 | 保留即可（新 k 下与中心公式自动连续）|
| 拖动侧 `wmin` | `max(minspan/dur, ov_min_px/rw)` | 不动 |

**归因（为什么前代没拟合出来）三条**，详见总账 §2.8：① 把 k 当成 u 的函数而不是 w 的函数（短片 w=0.405 → k=1.19；长片 w=0.700 → k=0.60）；② 拿一个随片长变的 k05 当常数去拟合 k(u)；③ 没人问「k 该不该从端点对齐反推」。
