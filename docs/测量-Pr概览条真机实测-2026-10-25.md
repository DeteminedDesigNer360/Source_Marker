## 三、结论 1：入出点标记是**完全线性**映射（决定性）

可视范围 = 整片，把播放头 park 到无关位置后扫描 ruler 上的蓝色标记（5 min 素材 9000 帧）：

| 区间（帧） | 入点 x | 出点 x | 线性预测 x = 14 + 0.1384t |
|---|---|---|---|
| 0 ~ 900 | 14 | 138 | 14 / 138.6 |
| 2250 ~ 6750 | 325 | 948 | 325.4 / 948.2 |
| 8880 ~ 8999 | 1244 | 1260 | 1243.0 / 1259.5 |
| 4500 ~ 4530 | 637 | 640.5 | 636.8 / 641.0 |

15 min 素材（27000 帧）同样线性：`x = 11.7 + 0.04626·t`（0~13500 → 636、2250~6750 → 324、seek 20000 → 937）。

- 拟合式 **x = 14 + 0.1384 × t**（t 单位帧），残差 ≤ 1 px
- **没有幂律、没有饱和、没有最小宽度撑开**：31 帧的区间（4.3 px）在屏幕上照样分成两条独立标记

⇒ mpv 现状 `w = u^pow`（长素材 pow≈0.48 时 `u=0.87 → w=0.936` 视觉即满条）与 Pr 行为**完全不同**，这就是 P1 的根因，修法是**位置线性**。

## 四、结论 2：可视范围滑块 —— 像素宽度与时间跨度**非线性**

- 概览条下方那条深色细条是**可视范围滚动条**，两个圆环 = 可视窗口左右边界；拖动它们，右下角的区间帧数**完全不变**
- 滑块拖到最窄（环心距 22 px）时 seek ruler 两端：`6489` ~ `6532` ⇒ **可视跨度 43 帧**（5 min 素材）
- 全宽 1248 px 覆盖 9000 帧 = **7.2 帧/px**；最窄处 22 px 覆盖 43 帧 = **2.0 帧/px** ⇒ **非线性约 3.6 倍**
- 15 min：最窄 **44 帧**；60 min（23.976 fps，总 86467 帧）：最窄 **44 帧** ⇒ **最窄可视跨度与片长无关**

⇒ r47 把 `tl_min_frames` 定为 **40** 与 Pr 吻合（用户 m02961 的目测结论被精确印证）。

**注意区分**：§三说的线性是「入出点标记」，本节说的非线性是「可视范围滑块」—— Pr 里这是两个不同的控件。

## 五、结论 3：滚轮语义矩阵（本轮新增，决定性）

固定基线（`-Prep "dash:10"` 回到全片 W=1238.8；或 `eq:2` 到 W≈607），逐格推进并截图扫描环心：

### 5.1 缩放类（W = 两环环心距）

| 修饰键 | 方向 | 起始 W | 每格变化 | 性质 |
|---|---|---|---|---|
| **无** | up | 1238.8 / 607.5 / 295.0 | **−2 px** | 缩放（细） |
| **无** | down | 607.5 / 295.0 | **+2 px** | 缩放（细） |
| **Shift** | up | 1238.8 / 607.5 / 295.0 | **−10 px** | 缩放（粗） |
| **Shift** | down | 607.5 / 295.0 | **+10 px** | 缩放（粗） |
| **Ctrl** | up / down | 1238.8 / 607.5 | **±2 px** | **与无修饰完全相同** |
| **Ctrl+Shift** | up | 1238.8 | **−10 px** | 与 Shift 相同 |

**关键：步长是「固定像素」，与当前缩放级别无关** —— W=1238.8、607.5、295.0 三个档位下裸滚都是 2 px/格、Shift 都是 10 px/格。

### 5.2 平移类

| 修饰键 | 方向 | L | R | W |
|---|---|---|---|---|
| **Alt** | up | **+1 px/格** | **+1 px/格** | 恒定 |
| **Alt** | down | **−1 px/格** | **−1 px/格** | 恒定 |
| **Alt+Shift** | up | **+5 px/格** | **+5 px/格** | 恒定 |
| **Alt+Shift** | down | **−5 px/格** | **−5 px/格** | 恒定 |

两环**同向移动、宽度不变** = 平视窗左右滑动。Alt 决定「平移模式」，Shift 决定 5 倍速。

**为什么第一版误判 Alt「无效」**：那次跑在全片基线（W=1238.8），两端都已贴边，没有平移余地 ⇒ 看起来毫无变化。

### 5.3 键位类（比例步长，与滚轮机制不同）

| 键 | 序列 | 每步 | 锚点 |
|---|---|---|---|
| `=` | 1238.8 → 868.0 → 607.5 → 424.0 | **×0.700** | 播放头 |
| `-` | 154.8 → 224.8 → 324.8 → 466.5 | **×1.44** | 播放头 |

两者精确互逆（1/0.700 = 1.429 ≈ 1.44）。

### 5.4 从全片到最窄要多少格（30 min 素材，W 1238.8 → 22）

| 方式 | 格数 |
|---|---|
| 裸滚 / Ctrl | **608 格** |
| Shift | **122 格** |

⇒ 精确复现用户 m08026 的判断「15 min 全片到最窄需 120+ 格」。

### 5.5 接近最窄时的行为（2026-10-26 补测，回答「步长会不会变」）

Pr 的最窄 W 有硬下限 **22 px**（30 min 素材实测，正好对应最窄可视跨度 43~44 帧）。在下限附近连续滚，步长**不变**，只是被钳住：

| 组 | 起始 W | 输入 | 逐步 W | 判定 |
|---|---|---|---|---|
| a | 63.0 | 裸滚 up ×4 | 63.0 → 61.2 → 59.2 → 57.0 → 55.5 | **每格 −2 px 恒定** |
| b | 21.0 | 裸滚 up ×4 | 21.0 → 22.0 → 22.0 → 22.0 → 22.0 | **已到下限，钳制** |
| c | 21.0 | Shift+滚 up ×4 | 21.0 → 22.0 → 22.0 → 22.0 → 22.0 | **同样钳制在下限** |

⇒ 三条结论：

1. **步长与缩放级别完全无关**，W=63 处仍是 −2 px（此前已验证 1238.8 / 607.5 / 295.0）
2. **不存在「接近最小值时步长变小/变大」的机制** —— 用户怀疑的现象被数据推翻
3. 到下限后**任何修饰键的滚轮都无效**，只做钳制；`Shift` 的下限与裸滚一致（都是 22 px）

对 mpv 的意义：`tl_zoom_steps` 用比例步长本身没错（那是 mpv 自己的手感参数），但**下限必须硬钳**，且下限附近**不要做步长自适应** —— Pr 证明用户能接受「W=22 时一格跳 9%」。

**序号口径对照**：Pr 最小环心距 22 px；mpv 的 `tl_ov_min_px = 27`（`:95`）也是环心距口径，比 Pr 大 23%，可保留（mpv 环更粗）。

### 5.6 控制条宽度的影响（2026-10-26 补测：rw=1240 与 rw=969 两种条宽）

之前所有数据都只在 1280×800 最大化布局下采（条端 x=20..1260，`rw=1240`）。这次把 Pr 窗口改成 1000×680（条端 x=163..1132，`rw=969`）再测，得到两个新事实。

**事实 1：裸滚步长与条宽无关，仍是 −2 px/格。**

| 条宽 `rw` | 起始可视宽 | 输入 | 逐步 | 每格 |
|---|---|---|---|---|
| 1240（最大化） | 1238.8 | 裸滚 up | 1238.8 → 1236.8 → 1234.8 → 1232.8 | **−2 px** |
| 969（1000×680） | 76 | 裸滚 up | 76 → 75 → 73 → 70 | **−2 px** |

⇒ 「固定像素」这条结论**跨条宽成立**，不是 1240 专属。对 mpv 的意义：`V/rw × 常数` 里的 `rw` 用**当前实际条宽**即可，Pr 本身就是这么缩放的（绝对像素手感不随窗口变化）。

**事实 2：Pr 的这条只画「可视区间」本身，不画整片背景。**

证据（1000 窗口，y=665 单行亮度）：条体 49、背景 35、环 138。缩到中间档后，**只有可视区间那一段是 49，左右两侧都是 35**。

| 状态 | 亮度 ≥42 的连续段 | 说明 |
|---|---|---|
| 全片 | 163..1132（= 整个条端） | 可视 = 全片 |
| 缩到中间 | 572..942（w=371） | 只有可视段亮 |
| 再缩 | 757..832（w=76） | 同上 |
| 到最小 | 786..818（w=33） | 钳制 |

⇒ **这条是「可视范围滑块」，不是「整片 + 入出点区间」**。所以对标关系要分清：

- 要抄「区间位置 / 长度**线性**」 ⇒ 对标 **ruler 上的蓝色入出点标记**（§三，已测 5/15/60 min 三片长）
- 要抄「可视范围**非线性**」 ⇒ 对标**这条滑块**（§四，`w = u^0.478`）
- **mpv 的概览条（整片背景 + 当前区间高亮）在 Pr 里没有直接对应物**，是 mpv 自创的

⚠️ 因此 `tools\pr-bar-scan.py` 的「最长亮段 = 条端」判定在**非全片**状态下是错的 —— 它会把可视段当成条端，恒得 `w=1.000`。测可视段必须传 `--xr` 固定条端，或改用「亮度 49 段」判定。

**窗口几何会跟着变，滚轮注入点必须重定位：**

| 窗口 | Pr 占位 | 条端 | 环心行 y |
|---|---|---|---|
| 最大化 | (-8,-8) 1296×776 | 20..1260 | **691** |
| 1000×680 @ (140,60) | 140..1140 / 60..740 | 163..1132 | **665** |

本次一开始沿用默认 `-Y 693` 打空，所有帧纹丝不动 —— 改尺寸后必须先用一张截图定位 y。

## 六、结论 4：缩放锚点 = 播放头 + 边界钳制补偿（本轮新增）

固定 W≈607.5，裸滚 up 3 格，只改播放头位置：

| 播放头 x | L 变化 | R 变化 |
|---|---|---|
| 120（偏左，L 已贴边） | **0** | −2 px/格 |
| 640（居中） | +1 px/格 | −1 px/格 |
| 1160（偏右，R 已贴边） | **+2 px/格** | **0** |

⇒ **锚点是播放头**，两端按播放头在区间里的比例分摊位移。

### 6.1 边界钳制会让上下速率不对称（用户 m08026 / m08479 的现象）

播放头在 **0 s**（左端贴边），W≈607.5：

| 方向 | W 序列 | 每格 |
|---|---|---|
| **up** | 607.5 → 605.5 → 603.5 → 601.5 | **−2 px** |
| **down** | 607.5 → 608.5 → 609.5 → 610.5 | **+1 px** |

**1 : 2**。而播放头居中时是 **1 : 1**（up −2 / down +2）。

**机制**：Pr 每格要改 2 px，按播放头比例分给两端；
- **收缩**时，被钳住那一端的份额**转给另一端** ⇒ 另一端走满 2 px
- **扩张**时，被钳住那一端的份额**直接丢失** ⇒ 另一端只走 1 px

所以「上滚 1 格 ≈ 下滚 2 格」只在**播放头贴边**时成立 —— 用户的两次观察都对，是本文第一版只测了居中一种情况。

### 7.1 扫描器的两个致命坑（第一版数据全废的原因）

1. **窗口边框会被当成环壁**。Pr 窗口左右各有 1 px 边框在 `x=1` 和 `x=1278`，早期版本把它们配上对，算出 `L=26.5 R=1259.5` 这种「看起来很像」的假数据。现在强制 `x ∈ [5, 1274]`。
2. **环壁间距是 2..9 px，不是 ≤3 px**。环是空心圆，单行上是两段窄壁，间距 5~7 px；容差过严会一条都配不上（表现为 `NO-RINGS`）。

另：环只在 `y=684..704` 出现，且必须先 `raise` 到前台再截图，否则截到的是 DSH。

### 7.2 注入通道的三条硬事实

1. `danger-full-access` 下**外部 `keybd_event` / `SendInput` 真实生效**（`GetAsyncKeyState` 返回 `0x8000`）；`workspace-write` 下被 UIPI 静默丢弃，日志还照样打 PASS。
2. **AHK 常驻会让 Pr 完全收不到鼠标点击**（实测 `gui_click` 点播放头纹丝不动，杀掉 AHK 立刻恢复）。本轮的采样器完全不用 AHK。
3. **Keyviz 可以当按键状态示波器**（用户 m08479 指出的读法）：

| Keyviz 画面 | 含义 |
|---|---|
| 黑框下方**一条粗红带**（约占下半） | **已松开** |
| 红带消失，只剩 **1 px 红描边** | **按住中** |

实测 Alt down（−32768）/ up（0）两帧完全符合。注意它显示的是**最近按下的键**，松开后图标仍在，只能靠红带判断状态。

## 九、对 mpv 的启示

### 9.1 P1（概览条位置）

Pr 的入出点标记**完全线性**（§三）⇒ mpv 应删掉 `TL.bar_pow` / `TL.bar_k`，改成纯线性映射；

**P1 的测量数据已完备，不用再采**：5 min（9000 帧）/ 15 min（27000 帧）/ 60 min（86467 帧）三张片长的入出点蓝标记都实测过，残差 ≤1 px，31 帧差也能分出两条（不撑开、无最小宽度）。
最小宽度用 `tl_min_frames = 40` 转成比例后**在概览条绘制侧**单独钳制，不要掺进位置公式（否则反解与绘制会错位）。

### 9.2 NS1（滚轮缩放步长）

mpv 现在是**比例**步长（`tl_zoom_steps = "1.003,1.001,1.01"`），缩得越深每格的时间变化越小 —— 这正是「相对」感的来源。
Pr 是**固定像素**步长，换算成 mpv 的坐标系：

```
每格可视跨度变化 = V / rw × 2     (裸滚，Ctrl 同)
                   = V / rw × 10    (Shift)
每格平移           = V / rw × 1     (Alt)
                   = V / rw × 5     (Alt+Shift)
```

其中 `V` = 当前可视跨度、`rw` = 概览条像素宽。这正好是用户 m02828 要的「绝对」手感。

**下限必须硬钳**：§5.5 补测证明 Pr 到最窄 W=22 px 后步长不变、任何修饰键都只做钳制 ⇒ 不要做「步长自适应」。

### 9.3 缩放锚点

mpv 现在是 `tl_zoom_anchor = snap`（吸附到标记/播放头），方向是对的；但要补上 Pr 的**边界钳制补偿**：
收缩时被钳端的份额转给另一端，扩张时丢弃 —— 否则贴边时上下速率会意外变成 1:1。

### 9.4 需要先确认的事

- mpv 的 `rw` 随窗口变化，`V/rw × 常数` 要每帧重算
- 用户要求「和 Pr 一样做到 40 f 左右的最小缩放」，`tl_min_frames = 40` 已符合，不必再动
## 十、2026-10-26 补充：注入通道与二分判据（定稿）

本节记录「测可视区间长度」所需的通道与判据，全部为真机实测。

### 10.1 注入通道：只有 DSH 工具能进 Pr 的帧号输入框

| 注入方式 | 结果 |
|---|---|
| python `SendInput`（VK 码，如 `0x35`） | **完全无效**：帧号框数字不变，回车不退出编辑态 |
| python `SendInput`（`KEYEVENTF_UNICODE`） | **同样无效** |
| DSH `gui_click` + `gui_key ctrl+a` + `gui_type` + `gui_key enter` | **一次成功** |

⇒ 二分循环必须由 DSH 工具编排；python 只负责截图与像素扫描。

**两个必要条件（都踩过）**：

1. **Pr 必须在前台**。Pr 不在前台时 `gui_click` 只把窗口激活，后续按键被吞 —— 实测 `goto 54000` 执行完画面仍停在 `frame 41000`，误以为 goto 失效。
2. **截图前要显式把 Pr 拉回前台**：`ShowWindow(h, SW_MAXIMIZE=3)` + `SetForegroundWindow(h)` + 等 0.8 s，再 `ImageGrab.grab`；否则截到的是 DSH 自己的窗口。

### 10.2 `goto` 的语义（V1 重测）

| 操作 | 播放头 | thumb |
|---|---|---|
| `goto 54000` | `frame 53999` | `L=838.2  R=1259.5`（轨道右端 1265） |
| `goto 10000 / 30000 / 50000` | 对应帧 | `W` 恒为 421.2 |

- `goto` 只移动播放头，并让 Pr **自动滚动**把播放头露出来；**不改变 `W`**。
- 自动滚动的终点是「刚好露出播放头」，与轨道端差约 5 px；用户 m09517 确认这就算贴边。
- 结论：**缩放档位一旦设好，任意次 `goto` 都不会破坏它** —— 这是二分法成立的前提。

### 10.3 扫描器：只能用环配对，不能取「最左/最右亮像素」

`pr-thumb.py` 那种取整行最左/最右亮度 ≥ 阈值的做法，在非全片状态会把 **ruler 左端**当成 thumb 左沿，得到 `xl` 恒 28 的假数据，并由此推出「goto 会改变可视区间」的错误结论。

正确做法：`tools\pr-ring-scan.py <png> --y 686:700` —— 相邻两段窄壁间距合适即配对成环，环心为 `L`/`R`，`W = R - L`。

### 10.4 `gui_scroll` 可调档位，且精确可逆

| 动作 | `W` |
|---|---|
| 基准 | 421.5 |
| `up` 5 格 | 411.2（−10.3，约 −2 px/格） |
| `down` 5 格 | 421.5（**精确复原**） |

### 10.5 二分判据（V3 通过，二值性完美）

| `goto` | `L` | `R` | 判定 |
|---|---|---|---|
| 50000 | 826.8 | 1248.2 | 基准 |
| 48000 | 826.8 | 1248.2 | **在可视区间内**（一字不动） |
| 45000 | 740.5 | 1161.8 | 出界（Pr 滚动了） |
| 42000 | 740.5 | 1161.8 | 在可视区间内 |
| 40000 | 654.2 | 1075.2 | 出界 |

- **判据**：`goto f` 后 thumb 一字不动 ⇔ `f` 落在当前可视区间内。
- **不需要复位**：出界必然改变 thumb，下一步直接拿新状态当基准即可。
- 由 48000/50000 与 40000/42000 两组夹逼，这一档的可视跨度在 **6000~10000 帧**之间（精确值待下一次二分收敛）。

### 10.6 本轮作废的结论

| 曾写下的结论 | 实际 |
|---|---|
| 「`goto` 会让可视区间变化」 | **错**，是扫描器 bug 造成的假象；`W` 实际恒定 |
| 「左下角缩放下拉能改时间轴档位」 | **错**，用户 m09368 确认那是源监视器画面缩放 |
| 「python 注入可以驱动 Pr」 | **错**，见 10.1 |
