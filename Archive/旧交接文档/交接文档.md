# Source Marker 移交文档

**用途**：把本仓库移交给下一个工作区，用于「两个插件合并」。
**日期**：2026-10-06 ｜ **当前版本**：v1.0.0，已在 Premiere Pro 24.0.0 / Windows 上真机验证通过。

---

## 0. 接手前必须知道的三件事

1. **本仓库有两个工作区各自开发的产物**，各自建过 release。合并前先看清 §1 的归属表。
2. **最有价值的资产不是代码，是 §3 那 5 条被真机推翻的 API 假设**。它们无法从文档读出，
   也不在没装 Premiere 的机器上发现，重写一遍要再花 4 轮真机往返。
3. **ExtendScript 的返回值一律不可信**（`null`、`true`、文档承诺的 `0` 三者互相矛盾）。
   所有"操作成功"都必须用**产物或状态**核实，见 §6。

## 3. 核心资产：被真机推翻的 5 条假设

> 全部在 Pr 24.0.0 上实测。**没有一条能从官方文档读出来。** 改代码前务必先读这一节。

| # | 文档 / 直觉 | 真机实测 | 后果与修法 |
|---|---|---|---|
| 1 | `Time.timecode` 可直接生成时间码字符串 | **该属性不存在**（`undefined`） | 「跳到标记」会拿 `undefined` 去调 `scrubTo`。改为自算时间码，且**刻意绕开 `ticks`**（给 `.seconds` 赋值后 `.ticks` 是否重算无保证） |
| 2 | `setInPoint()` 可用返回值判断成败 | 返回 **`null`**，但写入实际成功 | 按返回值判断会误报失败 → 改为**写完读回比对** |
| 3 | `encodeProjectItem` 能按子剪辑范围导出 | 无论 `workArea` 传 `ENTIRE` 还是 `IN_TO_OUT`，**都导出主素材全长**（请求 50.040s，产物 125.675s） | 「一键导出」曾完全不可用 → 改为**临时序列 + `encodeSequence`**，实测 50.069s |
| 4 | `ProjectItem.deleteBin()` 能删除对象 | 对序列和项目项**都返回 `true` 却什么都不删** | 序列改用 **`Project.deleteSequence()`**；项目项走「移进临时 bin → 删 bin」。且**一律重新枚举核实** |
| 5 | `app.bringToFront()` 能把文件对话框置前 | **该方法不存在**（`undefined`） | ExtendScript 对话框没有置前杠杆 → 改用 **CEP 自己的 `window.cep.fs.showOpenDialog`**（挂在面板窗口上） |

### 附带确认的可用项（正面清单）

| 项 | 实测 |
|---|---|
| `qe.source.player` | `startScrubbing` / `scrubTo` / `endScrubbing` / `step` / `play` **五个全部存在** |
| `createSubClip` | **`time-objects`（`new Time(); t.seconds=x`）与 `ticks-string` 都能建出正确范围**；回读是「相对自身」（请求 2.000s → 回读 `0.000~2.000`） |
| `MarkerCollection.createMarker(t)` | **按「秒」解释**，不是 ticks。猜错的话标记会**静默**全堆到 0 秒 |
| `sequence.insertClip` / `Track.overwriteClip` | 均为 function，行为正确 |
| `createNewSequenceFromClips(name, [items], bin)` | 可用；但**传入的名字不一定会被采用**（实测传 `素材名.mp4 [00-00-10-00~00-01-00-01]`，返回的却是素材名——可能被忽略，也可能被特殊字符截断）。代码里事后用 `seq.projectItem.name = …` 再改一次 |
| `File.openDialog` / `Folder.selectDialog` | 可用（只是不置前） |

## 4. 我犯过的错误（过程性教训，比 API 更值得防）

| # | 错误 | 具体表现 | 正确做法 |
|---|---|---|---|
| 1 | **一次改两处，无法归因** | 同时改了 workArea 常量和导出策略，导出变好了，于是把功劳记在"枚举"上——**实际常量本来就是数字 0/1**，真正起作用的是换策略 | 一次只改一个变量；要同时改就先加日志把中间状态打出来 |
| 2 | **把"调用没抛异常"当成"事情办成了"** | 自检代码写 `try { sub.deleteBin(); } catch(e){}` 然后输出「（已删除）」——实际什么都没删 | 核实**状态**，不是核实**调用**：删完重新枚举、写完读回、导完量产物 |
| 3 | **信任返回值** | `setInPoint()` 返回 `null` 当成失败；`deleteBin()` 返回 `true` 当成成功（实际没删） | ExtendScript 返回值一律不信 |
| 4 | **误判根因两次** | 先怪 `createSubClip`（其实它是对的，是我按绝对值比对才误判）；后怪 workArea 枚举 | 定位靠"把中间状态读回来"，不靠"改完好了" |
| 5 | **自己的测试断言写错** | 反复出现：正则多写空格、mock 没把 bin 放进项目树导致"移动"看起来像"删除"、DOM 元素没先创建 | mock 必须**保真**：删除动作要真的改数组、bin 要真的在树里，否则测的是假象 |
| 6 | **改了代码忘记重装，跑的是旧版本** | 已装副本缺 3 个文件却毫无提示，白排查一轮 | CEP 加载的是**安装目录那份**。`install.ps1` 已加逐文件 MD5 校验来暴露这件事 |
| 7 | **异步断言没 await** | 验证脚本里 `.then()` 的断言在程序退出后才跑，于是"验证通过"其实没验 | 用 `await`；程序输出看不到预期行时先怀疑这个 |

### 一条方法论

> 凡是「某个 API 帮我做成了某事」的地方，最终都改成**做完之后把状态读回来核实**：
> 导出时长去解析产物 MP4 的 `mvhd`，删除去重新枚举项目树，写入去读回比对。

## 5. 契约与不可破坏点（合并红线）

### 5.1 `main.js` 里的两条注释标记 —— 会被下游工具用来切代码段

`tools/pr-parser.js` 用 `indexOf` 定位，**必须保持这两行的前缀逐字符不变**：

```javascript
/* ------------------------------ 时间解析 ------------------------------ */
...
/* ------------------------------ 状态刷新 ------------------------------ */
```

它把这两行之间的整段代码在 Node `vm` 里求值，导出 `parseMarkerFile` / `secondsToTimecode` /
`parseTimeToSeconds` / `buildImportPayload` 供测试直接调用。
**改这一段里的代码结构 = 同时改所有下游验证工具。** 改完必须跑 `node tools/verify-import.js`。

同一段里还有一条隐含约束：**不能有依赖 DOM/window 的顶层副作用**（`var SET = readSettings();`
这种已在 try/catch 里，是安全的写法范例）。

### 5.2 宿主传输协议（面板 ↔ ExtendScript）

| 方向 | 协议 |
|---|---|
| 面板 → 宿主 | 函数调用，参数用 `q()` 转义 |
| 宿主 → 面板 | `"OK" + US + f1 + US + f2…` 或 `"ERR" + US + msg`，US = `\x1f` |
| 标记 payload | **记录用 `\n` 分隔，字段用 US 分隔**，字段顺序固定 `秒 \| 名 \| 注释 \| 颜色` |
| 标记列表回传 | `count=N` + 记录用 `GS(0x1d)` 分隔，记录内字段用 `RS(0x1e)` 分隔 |
| 字段折叠 | 面板在送宿主前把字段里的 CR/LF/US 折叠成空格（`buildImportPayload`），否则含换行的备注会被拆成两条 |

`buildImportPayload` 的行为被 `tools/verify-import.js` 用 7 条断言钉死（行数、字段数、3 位小数、
折叠、TAB 保留、超长字段、颜色 clamp 到 0..7）。**改它之前先看那些断言**。

### 5.3 标记命名规则（读取方行为，用户明确要求）

> ⚠️ **本节已被合并版推翻**（详见 `source-marker-united-1.0.1-alpha/改动说明.md`）。
> `M01` 占位符机制已**整体删除**：Pr 面板现在**整列忽略 `name`**，标记名只取 `comment`，
> 写入方保留该列但写空。下表是**合并前**的行为，保留作历史记录，不要再照它实现。

| 文件字段 | 落到 Pr 标记 |
|---|---|
| `comment` / 内容（非空） | **标记名** |
| `name` 且形如 `M01` | **丢弃** |
| `name` 且是用户自填 | 移到标记的**注释**里保留 |
| `comment` 为空 | 用 `name` 当标记名 |

### 5.4 打包与脚本

- **扩展 ID `com.frisk.sourcemarker`**，安装路径
  `C:\Program Files\Common Files\Adobe\CEP\extensions\com.frisk.sourcemarker`。
  新手版与完整版**共用此 ID，互相覆盖**。
- **`.ps1` 必须带 UTF-8 BOM**。Windows PowerShell 5.1 对无 BOM 的脚本按 ANSI(CP936) 解码，
  中文串被拆坏 → **语法错误 → 整份脚本跑不起来，且报错本身是乱码**。本项目踩过一次。
  仓库里有 `tools/ensure-ps1-bom.ps1` 做全仓自检。
  **注意：`write`/`edit` 工具会抹掉 BOM**，改完 `.ps1` 必须补回。
- **`.cmd` 相反，不能带 BOM**（否则 `@echo off` 会失效）。本仓库的 `install.cmd` 刻意全 ASCII。

## 7. 合并操作建议

### 7.1 先决定的三件事

1. **分发形态**：一个合并包（Pr 面板 + mpv 播放器一起给），还是两个独立下载？
   现状是 mpv 包 23.5MB（含播放器本体），Pr 扩展包 40KB，混在一起会让只想用一边的人多下 23MB。
2. **`release/` 的写入权**：指定一方统一出包，或强制各自独立子目录。
3. **`docs/marker-format.md` 的维护权**：它是两侧共同契约，改它必须同步改两侧读取/写入代码，
   并重跑 `verify-import.js`（读取方 28 条）与 `player-plugin/test/`（写入方）。

### 7.2 合并时的具体检查清单

- [ ] 两侧的 `.ps1` 都带 BOM（跑 `tools/ensure-ps1-bom.ps1 -CheckOnly`）
- [ ] `extension/client/main.js` 的两条注释标记未被破坏
- [ ] `node tools/verify-import.js` 仍 28/28
- [ ] `extension/host/hostscript.jsx` **与 `backup/…/hostscript.jsx` 逐字节一致**
      （除有意改动外——发布版引擎 = 真机验证过的引擎，这是刻意的约束）
- [ ] 解压测试：两个 zip 解压后逐文件哈希一致，且 `install.ps1 -DryRun` 退出码为 0
- [ ] `release/SHA256SUMS.txt` 的覆盖范围写清楚（目前只覆盖 Pr 扩展的两个包，**不含 mpv 包**）

### 7.3 如果要改 Pr 面板

- 宿主脚本（引擎）与面板（界面）是分离的，**优先只改界面**。
  新手版就是这么做的：界面重写，引擎逐字节未动，因此"简化"没有引入任何新的真机风险。
- 改完界面跑一次 `node tools/verify-import.js`（它会加载 `main.js`）。
